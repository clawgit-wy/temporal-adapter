## 1. 系统架构概览

### 1.1 整体架构图

```
┌─────────────────────────────────────────────────────────┐
│                    前端 Vue3 应用 (safety-web-master)        │
│  ┌──────────────────────────────────────────────────┐    │
│  │              menuData.ts 路由配置                  │    │
│  │  /buildingAccess/* → 楼宇门禁全部子路由             │    │
│  └──────────────────────────────────────────────────┘    │
│         ↓ defHttp.post/GET (axios HTTP 客户端)             │
└─────────────────────────────────────────────────────────┘
         ↓ HTTP/HTTPS (带 X-Access-Token 认证头)
┌─────────────────────────────────────────────────────────┐
│                  后端 Spring Boot (safety-service-master)    │
│  ┌─────────────┐  ┌──────────────┐  ┌────────────────┐  │
│  │  Controller  │→│   Handler     │→│    Service     │  │
│  │  (REST API)  │  │  (业务编排)   │  │  (数据操作)     │  │
│  └─────────────┘  └──────────────┘  └────────────────┘  │
│         ↓ MyBatis Mapper/XML                              │
│  ┌──────────────────────────────────────────────────┐    │
│  │              MySQL 数据库 (Safety Schema)          │    │
│  └──────────────────────────────────────────────────┘    │
│         ↓ 3DES + SHA256 加密签名                             │
│  ┌──────────────────────────────────────────────────┐    │
│  │        第三方门禁系统 (新开普/XinKaiPu) API          │    │
│  │        - 设备同步、权限下发、权限回收                  │    │
│  └──────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────┘
```

### 1.2 技术栈

| 层级 | 技术 | 版本/说明 |
|------|------|-----------|
| 前端框架 | Vue 3 + TypeScript | Composition API |
| UI 组件库 | Ant Design Vue | 企业级 UI |
| 前端构建 | Vite | 开发服务器 & 构建 |
| HTTP 客户端 | Axios | defHttp 封装 |
| 后端框架 | Spring Boot | DI/MVC/AOP |
| ORM | MyBatis | Mapper + XML 映射 |
| 数据库 | MySQL | 主数据库 |

| 工作流 | BPM (JeecgBoot) | 审批流程引擎 |
| 加密 | 3DES + SHA256 + Base64 | 第三方 API 通信加密 |
| 消息 | 宇信通 (YxtRebot) | 企业消息通知 |
| Excel | Apache POI + EasyExcel | 导入导出 |

## 3. 功能模块详细分析

### 3.1 基础信息管理 (BaseInfo)

#### 3.1.1 门禁管理 (AccessManage)

**前端组件**: `src/views/buildingAccessControl/baseInfo/accessManage/index.vue`
**API 文件**: `src/views/buildingAccessControl/baseInfo/accessManage/accessManage.api.ts`

**功能描述**:
管理楼宇门禁设备的基础信息，包括设备的增删改查、导入导出、权限克隆等操作。设备数据从第三方门禁系统（新开普）定时同步，本地保存扩展信息。

**API 接口**:

| 方法 | 前端 API 路径 | 后端 Controller 路径 | HTTP 方法 | 功能 |
|------|--------------|---------------------|-----------|------|
| 列表查询 | `/build/safety/buildDevice/list` | `SafetyBuildDeviceController.list()` | POST | 分页查询门禁列表 |
| 新增门禁 | `/buildingAccess/accessManage/add` | (前端直连) | POST | 新增门禁记录 |
| 编辑门禁 | `/build/safety/buildDevice/update` | `SafetyBuildDeviceController.update()` | POST | 编辑门禁信息 |
| 单个删除 | `/buildingAccess/accessManage/delete` | (前端直连) | POST | 删除单个门禁 |
| 批量删除 | `/buildingAccess/accessManage/deleteBatch` | (前端直连) | DELETE | 批量删除门禁 |
| 导出 | `/build/safety/buildDevice/exportForAn` | `SafetyBuildDeviceController.exportForAn()` | GET/POST | 导出 Excel |
| 导入 | `/buildingAccess/accessManage/import` | (前端直连) | POST | 批量导入门禁 |
| 下载模板 | `/buildingAccess/accessManage/download` | (前端直连) | GET | 下载模板 |
| 克隆设备 | `/build/safety/buildDevice/getCopyDeviceInfo` | `SafetyBuildDeviceController.getCopyDeviceInfo()` | GET/POST | 获取克隆源信息 |
| 提交克隆 | `/build/safety/buildDevice/submitCopyData` | `SafetyBuildDeviceController.submitCopyData()` | GET/POST | 克隆权限提交 |

**核心业务流程**:
1. **设备同步**: 定时任务从第三方系统拉取设备列表（分页500条/页），按区域分组，与本地数据库比对更新
2. **权限克隆**: 将源设备的所有权限复制到目标设备，自动过滤已存在的权限记录
3. **新设备通知**: 新设备入库后，通过宇信通机器人通知对应厂区的保卫主管

**后端 Handler**: `SafetyBuildDeviceHandler`
- 方法 `pageList()` - 分页查询，关联查询责任部门信息
- 方法 `updateDeviceTask()` - 定时全量同步第三方设备
- 方法 `submitCopyData()` - 权限克隆
- 方法 `sendMessageForNewDevice()` - 新设备通知

**数据模型**: `SafetyBuildDeviceDO`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String | 主键 UUID |
| deviceCode | String | 设备编码（第三方分控器ID） |
| deviceName | String | 设备名称 |
| factoryName | String | 厂区名 |
| factoryCode | String | 厂区编码 |
| building | String | 楼栋 |
| securityLevel | String | 保密等级 |
| deviceStatus | String | 状态：在线/离线 |
| removeFlag | String | 是否拆除：0-否/1-是 |
| deviceType | String | 设备类型：1-新开普/2-富士 |
| anDeviceName | String | 安保平台定义的设备名 |
| anBuilding | String | 安保平台定义的楼栋 |
| areaId | Integer | 区域ID |
| areaName | String | 区域名称 |
| termId | Integer | 终端ID |
| termAddr | String | 终端IP |
| levf | Integer | 区域层级：1园区/2楼栋/3单元/4楼层/5房间 |

### 3.3 楼宇门禁申请流程 (Access Request Process)

#### 3.3.1 申请流程列表

**前端组件**: `src/views/buildingAccessControl/accessRequestProcess/index.vue`
**API 文件**: `src/views/buildingAccessControl/accessRequestProcess/accessRequest.api.ts`

**功能描述**:
展示当前用户参与的楼宇门禁权限申请流程列表，支持按状态（草稿/审批中/已发布/已废弃）筛选。

**API 接口**:

| 方法 | 前端 API 路径 | 后端 Controller 路径 | 功能 |
|------|--------------|---------------------|------|
| 列表查询 | `/build/safety/buildProcess/getPageList` | `SafetyBuildProcessController.getPageList()` | 分页查询流程 |
| 角色校验 | `/build/safety/buildProcess/checkBuildRoleType` | `SafetyBuildProcessController.checkBuildRoleType()` | 校验用户角色 |
| 导出 | `/build/safety/buildProcess/exportList` | `SafetyBuildProcessController.exportList()` | Excel 导出 |
| 流程详情 | `/build/safety/buildProcess/viewProcessMain` | `SafetyBuildProcessController.viewProcessMain()` | 查询流程主体 |

**流程状态流转**:
```
草稿 (10) → 审批中 (20) → 已发布 (30) → 已下发 → 已废弃 (00)
                                    ↑
                               审批节点拒绝
                                    ↓
                               草稿 (10) 或 废弃 (00)
```

**审批节点顺序**:
N1 → N2 → N5 → N11 → N16 → N30 (发布)

| 节点 | 说明 |
|------|------|
| N1 | 发起部门负责人审批 |
| N2 | 部门负责人审批 |
| N5 | 保密负责人审批 |
| N11 | 跨部门负责人审批（如涉及） |
| N16 | 门禁系统管理员审批 |
| N30 | 系统自动发布（权限下发） |

#### 3.3.2 楼宇门禁申请表单 (Form)

**前端组件**: `src/views/buildingAccessControl/accessRequestProcess/form/index.vue`
**API 文件**: `src/views/buildingAccessControl/accessRequestProcess/form/`

**功能描述**:
门禁权限申请的表单页面，支持两种授权模式：
1. **指定人员授权**: 直接选择员工进行授权
2. **组织批量授权**: 按部门/组织批量授权，自动获取该组织下所有员工

**后端方法**: `SafetyBuildProcessHandler.saveAndCreateProcessByUserName()`

**核心流程**:
1. 表单数据校验
2. 用户权限校验（门禁管理员只能管理自己负责的门禁）
3. 白名单校验（白名单人员不可提交关闭权限）
4. 保存流程主记录和明细（开通/关闭列表）
5. 调用 BPM 引擎创建审批流程
6. 发送消息通知

**API 接口**:

| 方法 | 前端 API 路径 | 后端 Controller 路径 | 功能 |
|------|--------------|---------------------|------|
| 保存并创建流程 | (表单提交) | `SafetyBuildProcessController.saveAndCreateProcess()` | 保存+发起 BPM |
| 审批流程 | (审批操作) | `SafetyBuildProcessController.auditProcess()` | BPM 审批 |
| 部分审批 | (批量审批) | `SafetyBuildProcessController.auditPartProcess()` | 批量通过 |

**数据模型**: `SafetyBuildProcessDO` (流程主表)

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String | 主键 UUID |
| bpmFlowId | String | BPM 流程实例 ID |
| processCode | String | 流程编码 LYMJSQ+日期+序号 |

## 5. Temporal 工作流重构分析

### 5.1 当前系统痛点分析

#### 5.1.1 大规模数据权限下发的性能瓶颈

**问题描述**:

在 `SafetyBuildProcessHandler.dealBuildOpenList()` 方法中，当流程审批通过后，系统需要处理可能上千员工的门禁权限下发。当前实现存在以下问题：

1. **同步阻塞**: 权限下发是同步执行的，导致 BPM 流程审批回调超时
2. **批次限制**: 新开普接口每批最多 200 个设备，大量权限需要分多批串行调用
3. **无并发控制**: 所有权限串行下发，即使不同员工的权限之间无依赖
4. **失败隔离差**: 单个员工下发失败不影响其他，但整体流程状态变为"异常"

**代码位置**:
- [SafetyBuildProcessHandler.java](file:///Users/apple/Desktop/AdapterService/demos/safety-service-master/safety-core/src/main/java/com/yutong/safety/core/handler/build/SafetyBuildProcessHandler.java) - `dealBuildOpenList()` (L918-L1003)
- [SafetyBuildIssuedLogService.java](file:///Users/apple/Desktop/AdapterService/demos/safety-service-master/safety-core/src/main/java/com/yutong/safety/core/service/build/SafetyBuildIssuedLogService.java) - `issuedBuildPower()` (L90-L137)

#### 5.1.2 第三方 API 可靠性挑战

**问题描述**:

`BuildEncryptUtil.sendBuildHttpPost()` 方法中存在以下可靠性问题：

1. **简单重试**: 仅重试 1 次，总尝试 2 次即放弃
2. **无退避策略**: 重试间隔固定，无指数退避
3. **无超时控制**: HTTP 调用无显式超时配置
4. **状态不一致**: 第三方已成功处理但网络超时，本地记录为"异常"，导致重复下发
5. **无幂等保障**: 重复调用可能导致权限叠加

**代码位置**:
- [BuildEncryptUtil.java](file:///Users/apple/Desktop/AdapterService/demos/safety-service-master/safety-common/src/main/java/com/yutong/safety/common/utils/BuildEncryptUtil.java) - `sendBuildHttpPost()` (L301-L335)

#### 5.1.3 手动补偿机制缺陷

当前"手动下发"功能 (`SafetyBuildIssuedLogHandler.downBySelf()`) 存在：
1. 仅支持全量重试，不支持按单条或批量筛选重试
2. 无失败原因分类和针对性处理
3. 无优先级调度（紧急权限无法优先下发）
4. 操作不可撤销

### 5.2 Temporal 重构候选方案

#### 候选 1: 门禁权限下发工作流 (Permission Distribution Workflow)

**重构理由**:

将权限下发从同步阻塞改为 Temporal 异步工作流，解决大规模数据下发的性能和可靠性问题。

**当前实现** (`issuedBuildPower`):
```java
// 当前：同步串行调用
partition.forEach(li -> {
    String curDevice = li.stream().collect(Collectors.joining(","));
    // 直接 HTTP 调用第三方
    String retStr = BuildEncryptUtil.sendBuildHttpPost(grantBuildUrl, ...);
    // 立即记录结果
});
```

**Temporal 工作流设计**:

```java
@WorkflowInterface
public interface PermissionDistributionWorkflow {
    
    @WorkflowMethod
    void distributePermissions(PermissionDistributionRequest request);
    
    @SignalMethod
    void retryFailedItems(List<Integer> failedLogIds);
    
    @QueryMethod
    DistributionProgress getProgress();
}
```

**工作流状态机**:

```
[INIT] 
  → [VALIDATE_REQUEST]     校验参数、设备有效性
  → [CHECK_WHITELIST]      白名单校验
  → [CREATE_ISSUE_LOGS]    批量创建下发日志 (数据库持久化)
  → [DISTRIBUTE_IN_PARALLEL] 并行下发 (按员工分组)
      ├── Activity: distributeSingleEmployee() ← 带重试、超时
      ├── Activity: distributeSingleEmployee()
      └── ... (最多 50 并发)
  → [AGGREGATE_RESULTS]     汇总下发结果
  → [UPDATE_PROCESS_STATUS] 更新流程状态
  → [NOTIFY_COMPLETION]     发送通知
  → [COMPLETED]
  
异常路径:
  [DISTRIBUTE_IN_PARALLEL] → [SUSPENDED] → (手动重试) → [RESUME]
```

**Activity 定义**:

| Activity | 职责 | 重试策略 | 超时 |
|----------|------|----------|------|
| `validateRequest` | 校验流程、设备、员工有效性 | 无 | 30s |
| `createIssueLogs` | 批量创建下发日志记录 | 最多 3 次/指数退避 | 2min |
| `distributeSingleEmployee` | 单个员工权限下发 | 最多 5 次/指数退避 10s, 20s, 40s, 80s, 160s | 5min |
| `aggregateResults` | 汇总下发结果 | 最多 3 次 | 1min |
| `updateProcessStatus` | 更新流程状态为"发布" | 最多 3 次 | 30s |
| `notifyCompletion` | 发送完成通知 | 最多 2 次 | 30s |

**核心 Activity: distributeSingleEmployee 设计**:

```java
@ActivityInterface
public interface PermissionActivities {
    
    /**
     * 下发单个员工的门禁权限
     * Temporal Activity 保证 at-least-once 执行
     * 通过外部幂等键确保第三方不会重复授权
     */
    @ActivityMethod
    DistributionResult distributeSingleEmployee(EmployeePermissionRequest request);
}
```

**幂等保障方案**:
- 为每次下发生成唯一 `distributiomId = processId + employeeCode + batchIndex`
- 调用第三方 API 时将 `distributiomId` 作为备注参数传递
- 第三方系统需支持基于 `distributiomId` 的幂等检查
- 若第三方不支持，采用"查询 + 条件下发"模式：
  1. 先查询员工当前权限 (`GetGrantInfo`)
  2. 对比目标权限，计算差集
  3. 仅下发差集中的新增权限

**改进效果**:

| 指标 | 当前 | Temporal | 提升 |
|------|------|----------|------|
| 100 人权限下发耗时 | ~30 min | ~3 min | 10x |
| 500 人权限下发耗时 | ~2.5 h | ~10 min | 15x |
| 第三方异常处理 | 手动重试 | 自动重试+手动干预 | 显著 |
| 流程审批超时风险 | 高 | 无 | 消除 |
| 权限一致性保障 | 弱 | 强 (Temporal 保证) | 显著 |
| 可观测性 | 低 | 高 (Temporal UI) | 显著 |

#### 候选 2: 设备数据同步工作流 (Device Sync Workflow)

**重构理由**:

`updateDeviceTask()` 方法中，设备同步采用固定 500 条/页的串行方式，且异常处理仅记录日志，缺乏补偿机制。

**当前实现**:
```java
// 固定分页大小
int buildPageSize = 500;
int totalPage = 1;

// 串行拉取每页数据
for (int i = 1; i <= totalPage; i++) {
    JSONObject returnObj = sendBuildDevicePost(buildPageNo + i, buildPageSize, areaId);
    // 异常仅记录日志，无补偿
}
```

**Temporal 工作流设计**:

```java
@WorkflowInterface
public interface DeviceSyncWorkflow {
    
    @WorkflowMethod
    SyncResult syncDevices(SyncRequest request);
}
```

**工作流状态机**:

```
[INIT] → [FETCH_TOTAL_COUNT]
  → [FETCH_PAGES_PARALLEL] 并行拉取各页
      ├── Activity: fetchPage(1)
      ├── Activity: fetchPage(2)
      ├── ...
  → [MERGE_AND_SAVE] 合并各页结果
  → [DIFF_AND_UPDATE] 差异比对，更新本地库
  → [DISABLE_REMOVED] 标记已移除设备
  → [NOTIFY_ADMINS] 通知新增设备
  → [COMPLETED]
```

**改进效果**:

| 指标 | 当前 | Temporal |
|------|------|----------|
| 设备同步耗时 (5000 台) | ~10 min | ~2 min |
| 单页失败影响 | 全部中止 | 仅单页重试 |
| 增量同步支持 | 无 | 支持 (基于 updateTime) |
| 可中断性 | 不支持 | 支持 |

#### 候选 3: 权限全量初始化工作流 (Permission Init Workflow)

**重构理由**:

`initEmployeePower()` 和 `initCrkBuildPower()` 方法需要全量拉取所有员工的门禁权限，数据量巨大（可能上万员工），且需要从两个不同的第三方系统（新开普和富士）获取。

**当前实现**:
- 固定 500 条/页
- 串行遍历所有页
- 内存中维护完整列表
- 异常丢失数据

**Temporal 工作流设计**:

```java
@WorkflowInterface
public interface PermissionInitWorkflow {
    
    @WorkflowMethod
    InitResult initAllPermissions(InitRequest request);
    
    @SignalMethod
    void resumeAfterPause();
}
```

**工作流状态机**:

```
[INIT] 
  → [INIT_XKP_PERMISSIONS]     新开普权限初始化
      → [FETCH_AND_SAVE_PARALLEL] 并行分页
  → [INIT_CRK_PERMISSIONS]     富士权限初始化
      → [FETCH_AND_SAVE_PARALLEL] 并行分页
  → [MERGE_DEDUP]              合并去重
  → [VALIDATE_INTEGRITY]       数据完整性校验
  → [COMPLETED]
```

**核心优势**:
- 可暂停和恢复（长时间运行的工作流）
- 部分完成数据可持久化（Temporal checkpoint）
- 支持增量更新（基于 updateTime 时间戳）
- 进度可查询

---

#### 候选 4: 人员变更确认批量处理工作流

**重构理由**:

`SafetyBuildDepartConfirmHandler.batchDealBuild()` 处理人员变动时需批量调用第三方 API，可能涉及大量人员和设备。

**Temporal 工作流设计**:

```java
@WorkflowInterface
public interface DepartConfirmWorkflow {
    
    @WorkflowMethod
    ConfirmResult processDepartChanges(DepartConfirmRequest request);
}
```

**工作流状态机**:

```
[INIT] → [GROUP_BY_DEPART] 按部门分组
  → [PROCESS_GROUPS_PARALLEL] 并行处理
      ├── [VALIDATE_GROUP]     校验部门数据
      ├── [DISTRIBUTE_PERMISSIONS] 下发权限 (复用候选1的 Activity)
      └── [SEND_NOTIFICATIONS]  发送通知
  → [AGGREGATE_RESULTS]
  → [COMPLETED]
```

## 7. 总结与建议

### 7.1 系统当前状况

楼宇门禁系统是一个功能完整的企业级门禁权限管理平台，覆盖了从设备管理、权限申请、审批下发到异常确认的完整闭环。系统与第三方门禁厂商（新开普/富士）进行了深度集成，通过加密 API 通信实现设备同步和权限远程下发。

**优势**:
- 完整的 RBAC 权限体系（管理员/保密负责人/员工）
- 成熟的 BPM 审批流程
- 灵活的白名单/黑名单管理
- 完善的日志追踪和手动补偿机制

**局限**:
- 大规模数据权限下发性能不足
- 第三方 API 可靠性处理不够健壮
- 权限下发与审批流程紧耦合
- 缺乏实时可观测性

### 7.2 Temporal 改造优先级建议

1. **立即实施**: 候选 1 (权限下发工作流) - 解决最紧迫的性能和可靠性问题
2. **其次实施**: 候选 2 (设备同步工作流) - 提升数据同步效率
3. **后续实施**: 候选 3 + 候选 4 - 完善全链路工作流化改造

### 7.3 风险与缓解

| 风险 | 缓解措施 |
|------|----------|
| Temporal 学习曲线 | 先 POC 验证，再推广；可招聘/培训团队 |
| 双写期间数据不一致 | 设置对比脚本，定期校验 Temporal 与旧逻辑结果 |
| 第三方 API 不支持幂等 | Activity 内实现"查询+条件下发"逻辑 |
| 运维复杂度增加 | 引入 Temporal UI 监控；编写自动告警脚本 |
| 迁移期间生产稳定性 | 严格灰度 + 可回滚配置开关 |
