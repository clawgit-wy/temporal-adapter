1.1 我们的业务现状
!

我们的核心业务是宇通安保管理平台，涉及门禁系统的人员权限批量管理、海康威视人脸识别中台同步、访客/外来人员入厂备案等多个业务域。系统覆盖 4 万+ 在职人员，对接 500+ 门禁设备（分属新开普和富士两个门禁厂商接口），经常面临 1000+ 人的权限数据批量下发场景。

!

1.2 业务场景中的六大痛点
!

以下每个痛点均以技术分析报告中迁移评分 ≥ 17 的实际业务场景作为案例支撑。

!

!

痛点一：第三方接口被打垮（限流失控）
!

案例场景：海康人脸分组批量同步（迁移评分 24/25）+ 楼宇门禁权限批量管理（21/25）

!

!

海康人脸同步：系统有 4 万+ 在职人员，定时任务（SafetyHikJobController）每 30 分钟执行一次外来人员人脸分组变更，另有全量在职人员分组数据更新任务。当前实现使用 @Async + batchExecutorService 线程池（核心 5 / 最大 10 / 队列 200），无速率限制，大批量调用时直接冲击海康 Artemis API。海康 SDK 仅提供单人操作接口，4 万人全量更新即 4 万次 API 调用，瞬间并发可能打垮海康中台或触发 429 限流。

!

楼宇门禁权限下发：经常面临 1000+ 人的权限数据批量下发，每人涉及 500+ 门禁设备（新开普 + 富士两个厂商接口），单次批量操作即产生 50 万+ 次 API 调用。当前新开普门禁接口仅重试 1 次，富士门禁接口无任何重试，且无全局速率控制。

!

  • 传统方案：手动维护信号量（Semaphore）、线程池，代码侵入性强
  • 问题：限流逻辑散落在业务代码中，难以统一管控和动态调整；不同接口限流策略不一致
    • !

痛点二：接口故障时重试逻辑复杂（代码膨胀）
!

案例场景：BPM 流程编排（17/25）+ CRK 出入口权限管理（17/25）+ 海康人脸同步（24/25）

!

!

经技术分析发现，项目中 30+ 个外部系统集成点的重试机制严重不一致：

!

!
集成系统 API 模式 当前重试 问题
海康 Artemis SDK REST 无 人脸分组/添加/检索失败即丢，数据不一致
BPM 流程引擎 SOAP 无 流程创建/审批失败需人工干预
CRK 出入口系统 REST 无 权限下发失败影响访客入场
EHR 人力资源 REST (OAuth2) 无 Token 获取失败影响后续所有操作
IAM 身份中台 REST 无 员工/组织/短信/邮件调用失败即丢
新开普楼宇门禁 REST (3DES) 仅 1 次 retcode != 200 时重试 1 次，不够
文件上传 (zoffice) HTTP multipart 3 次 唯一有完整重试的组件
  • 传统方案：手写 try-catch + for 循环重试 + 指数退避
  • 问题：每个接口调用点都要写一遍，漏写就没有重试；30+ 个集成点中仅 2 个有重试逻辑，可靠性债务极其严重
    • !

痛点三：多步骤编排与顺序依赖难以保证（流程断裂）
!

案例场景：楼宇门禁权限管理（21/25）+ 入厂备案权限下发（23/25）

!

!

楼宇门禁 17 个定时任务（SafetyBuildJobController）存在复杂的执行顺序依赖：

!

updateDeviceTask（每天更新设备）-> removeDevicePower（移除无效权限）
updatePowerTask（按组织自动授权）-> autoConfirmChangePower（自动确认权限）
modifyRecordsTask（更新出入记录）-> initBuildLongTerm（更新长期未进出）-> sendOwnerLongToDo（发送代办 9:10）-> closeOwnerLongToDo（超 7 天消除代办）

!

当前依赖 XXL-JOB 调度中心按 cron 顺序触发各 HTTP 端点，任务间无事务保证，前序任务失败后后续任务仍会执行，导致数据不一致。17 个端点的调度配置分散在 XXL-JOB 管理后台，维护成本极高。

!

入厂备案 6 个定时任务（SafetyEntryJobController）同样存在数据依赖：EHR 黑名单同步 -> 权限下发 -> Redis 清理，任一步骤失败影响整体业务。

!

  • 传统方案：XXL-JOB 按 cron 顺序触发，或 DB 状态字段串联
  • 问题：无事务保证，前序失败后续仍执行；流程状态分散在 DB 和内存中，排查困难
    • !

痛点四：长耗时等待浪费资源（定时任务笨重）
!

案例场景：入厂备案权限定时下发（23/25）+ 访客授权审批与定时下发（22/25）

!

!

入厂备案权限下发：entryPermissionDelegationTask 每 30 分钟执行一次，扫库查询"当前时间 +33 分钟"（预留 3 分钟时间差）内需要下发权限的备案人员。这意味着：

!

  • 每 30 分钟全表扫描一次，量大时产生 DB 慢查询
  • 扫库方式存在漏单风险：任务执行期间新预约的备案人员需等下一个 30 分钟周期
  • entryOverdueTask 每天 17:00 邮件提醒，需额外维护 cron 配置
    • !

访客授权定时下发：访客预约入场前 10 分钟需自动下发门禁权限，当前依赖 XXL-JOB 定时扫库（每分钟扫 status=PENDING 且 time <= 入场前10分钟），问题同上。

!

  • 传统方案：Quartz/XXL-JOB 定时扫库（每分钟或每 30 分钟扫一次）
  • 问题：扫库产生 DB 慢查询；量大时容易漏单；Thread.sleep() 白白占用线程和内存；时间精度受扫描间隔限制
    • !

痛点五：异步结果通知不可靠（回调丢失）
!

案例场景：海康批量操作完成后的结果回传 + BPM 审批结果通知

!

!

海康批量操作结果回传：批量人脸分组同步（4 万人）执行完后，需将成功/失败汇总结果回传给主业务系统并记录。当前 SafetyHikJobController 的任务通过 HTTP 触发，执行结果仅写入日志，无主动回调通知机制。如果主服务需要感知执行结果，需轮询查询或依赖宇信通消息推送，但宇信通消息推送本身也无重试机制。

!

BPM 审批结果：BPM SOAP 接口无重试，流程审批状态更新失败后无补偿机制，需人工排查。

!

  • 传统方案：Webhook 回调 + 定时补偿 Job 兜底
  • 问题：补偿 Job 需要额外开发和维护；Webhook 重试逻辑需要手写；当前系统连补偿 Job 都未实现
    • !

痛点六：主服务内存溢出（OOM 风险）
!

案例场景：海康人脸分组批量同步（24/25）

!

!

海康人脸识别服务（SafetyArtemisService）使用 @Async + batchExecutorService 线程池处理人脸操作。线程池配置为：核心 5 / 最大 10 / 队列 200 / CallerRunsPolicy。

!

当执行 4 万+ 人员全量分组更新时：

!

  1. 大量人脸图片 Base64 编码的 HTTP 请求对象堆积在 JVM 堆中
  2. 海康 API 响应慢（socket 超时 10s），未完成的 Future 持续积压
  3. 队列满后 CallerRunsPolicy 在调用线程执行，阻塞主流程
  4. 频繁 GC 甚至 OOM，影响整个主服务的稳定性
    5. !

楼宇门禁批量下发：1000+ 人 × 500+ 设备 = 50 万+ 次 API 调用，如果同步循环或无界线程池执行，同样会导致 JVM 堆积压 HTTP 请求对象与 Future，引发 OOM。

!

  • 传统方案：自建独立中转服务 + 手动限流（参见 Hikvision_Batch_Adapter_Design.md）
  • 问题：中转服务本身也需要处理重试、状态管理、补偿等全部可靠性问题；手写 Semaphore(15) + ThreadPoolExecutor + CompletableFuture 代码量大且易出错
    • !

二、解决方案：引入 Temporal
!

2.1 Temporal 是什么
!

Temporal 是一个开源的分布式持久化工作流引擎（Durable Execution Engine），它让开发者可以用普通代码编写复杂的多步骤业务流程，并由引擎 100% 保证每个步骤的可靠执行--无论过程中发生网络故障、服务器宕机、进程崩溃还是第三方接口超时。

!

核心理念：开发者只写业务逻辑（Happy Path），可靠性由引擎兜底。

!

3.1 痛点一解决方案：内置限流与削峰
!

对应场景：海康人脸分组同步（4 万+ 人员）+ 楼宇门禁权限下发（1000+ 人 × 500+ 设备 = 50 万+ 次 API 调用）

!

!

Temporal Worker 支持配置全局并发上限和每秒任务数限制，限流参数一行代码搞定，无需手写信号量：

!

Worker worker = factory.newWorker("HIK_BATCH_TASK_QUEUE",
    WorkerOptions.newBuilder()
        .setMaxConcurrentActivityExecutionSize(15)  // 全局并发不超过 15
        .setMaxWorkerActivityTasksPerSecond(20)     // 每秒最多 20 个任务
        .build());

!

效果：无论是 4 万人海康分组同步还是 1000 人 × 500 门禁 = 50 万次 API 调用，存入 Task Queue 排队缓冲，Worker 以恒定速率消费，绝不打垮新开普、富士或海康接口。即使瞬间涌入再多的请求，任务也只是在队列中排队，不会丢失、不会拒绝。

!

3.2 痛点二解决方案：自动指数退避重试（零代码）
!

对应场景：30+ 个外部系统集成点中仅 2 个有重试逻辑（海康/BPM/CRK/EHR/IAM 均无重试）

!

!

Temporal Activity 执行失败后自动按配置的重试策略进行指数退避重试，业务代码无需写一行重试逻辑：

!

第1次失败 -> 等1秒 -> 第2次失败 -> 等2秒 -> 第3次失败 -> 等4秒 -> 第4次成功 ✓

整个过程在 Web UI 上一目了然，业务系统完全无感知

!

超过最大重试次数后，Workflow 可优雅捕获并进入异常处理分支。无论是海康 SDK 调用、BPM SOAP 接口还是 CRK 权限下发，统一由引擎保证重试。

!

3.3 痛点三解决方案：多步骤编排与断点续传（零丢失）
!

对应场景：楼宇门禁 17 个任务的顺序依赖 + 入厂备案 6 个任务的数据依赖

!

!

Temporal 原生支持多步骤流程编排，顺序、并行、子流程均可声明式定义。Workflow 中的代码顺序即为执行顺序，前序 Activity 完成后才会执行后续 Activity，天然保证顺序依赖：

!

// 楼宇门禁 Workflow 示例：步骤顺序即执行顺序
@WorkflowMethod
public void executeBuildPowerWorkflow(String date) {
    // Step 1: 更新设备（完成后才执行 Step 2）
    activities.updateDeviceTask();
    activities.removeDevicePower();
    
    // Step 2: 更新权限（依赖 Step 1 的设备数据）
    activities.updatePowerByDate(date);
    activities.autoConfirmPower();
    
    // Step 3: 更新出入记录 -> 长期未进出 -> 发送代办（顺序依赖链）
    activities.modifyRecords();
    activities.initLongTerm();
    activities.sendOwnerLongToDo();
}

!

同时，Temporal 采用 Event Sourcing 模式，Workflow 的每一步执行结果都持久化到数据库。Worker 进程崩溃/服务器断电后重启，Temporal 自动从最后完成的步骤继续执行，已完成的 Activity 绝不会重复执行。

!

正常执行：  Step 1 ✓  ->  Step 2 (执行中) 💥崩溃
                     ↓ 服务器重启
恢复执行：  Step 1 (跳过)  ->  Step 2 (从头执行)  ->  Step 3 ✓

不会从头重新跑，也不会漏掉任何步骤

!

对比传统方案：XXL-JOB 按 cron 顺序触发 17 个独立 HTTP 端点，前序失败后续仍执行；Temporal 在一个 Workflow 内编排，前序失败后续不执行，且自动重试前序步骤。

!

3.4 痛点四解决方案：持久化定时器（零资源占用）
!

对应场景：入厂备案每 30 分钟扫库下发"当前时间+33分钟"权限 + 访客入场前 10 分钟下发权限

!

!

Workflow.sleep() 是持久化定时器，休眠期间 Worker 进程零 CPU、零内存占用。即使休眠 30 天甚至 1 年，资源消耗也是 0。休眠期间服务器断电，恢复后继续无缝倒计时，绝无漏单风险。

!

// 入厂备案权限定时下发：替代每 30 分钟扫库
// 计算预约入场时间前 33 分钟的等待时间，直接休眠
long delay = appointmentTime.minusMinutes(33).getTime() - Workflow.currentTimeMillis();
Workflow.sleep(delay);
// 时间一到，Temporal 自动唤醒，执行下发 Activity
entryActivities.delegatePermission(entryId, doorIds);

!
// 访客入场前 10 分钟下发权限：替代每分钟扫库
long delay = entryTime.minusMinutes(10).getTime() - Workflow.currentTimeMillis();
Workflow.sleep(delay);
visitorActivities.grantAccess(visitorId, doorIds);

!

对比传统方案：XXL-JOB 每 30 分钟扫库产生 DB 慢查询且有漏单风险；Workflow.sleep() 精确到毫秒，零资源占用，绝无漏单。

!

动态改期/取消：访客临时改期或取消，业务系统发送一个 Signal（信号），Workflow 自动取消旧定时器并按新时间重新休眠，或直接结束流程。

!

3.5 痛点五解决方案：可靠的 Webhook 回调
!

对应场景：海康批量操作完成后的结果回传 + BPM 审批结果通知

!

!

Webhook 回调本身就是一个 Activity。如果主系统宕机返回异常，Temporal 自动重试发送，直到主系统恢复返回 200。无需手写补偿 Job。当前系统中海康任务结果仅写日志、无主动回调的问题彻底解决。

!

3.6 痛点六解决方案：控制面与数据面分离
!

对应场景：海康人脸识别 4 万人全量更新导致 OOM + 楼宇门禁 50 万次 API 调用

!

引入 Temporal 后，主业务系统只需调用 StartWorkflow（一条 gRPC 指令，< 5ms 即返回），不持有任何长连接，彻底断开与海康/新开普/富士等下游 API 的耦合。真正消耗 CPU/内存的网络调用全部在独立的 Worker 集群中执行，主服务零 OOM 风险。

4.1 与 XXL-JOB / Quartz 对比
!

定位差异：XXL-JOB 和 Quartz 是定时任务调度框架，Temporal 是持久化工作流引擎。两者解决的不是同一类问题，但在"定时触发"和"任务可靠性"场景下有交集。

!

!
!
对比维度 XXL-JOB / Quartz Temporal
核心定位 定时任务调度（Cron 触发） 持久化工作流编排（全生命周期管理）
定时能力 基于 Cron 表达式定时触发 Workflow.sleep() 持久化定时器，精确到毫秒
长等待处理 需要线程一直 sleep，占用资源 休眠期间零资源占用，可等待数天/数月
任务重试 需手写重试逻辑 自动指数退避重试，零代码
断点续传 不支持，失败后需从头重跑 天然支持，从断点处自动恢复
多步骤编排 不支持（每个任务是独立的） 原生支持顺序/并行/子流程编排
人工审批 不支持 原生支持 Signal 等待与唤醒
状态可视化 只能看到任务执行日志 完整的 Event History + Web UI
动态取消/改期 需要手动停止任务 + 清理状态 Signal 一行代码，自动处理
扫库问题 高频扫库产生 DB 压力，可能漏单 无需扫库，定时器由引擎内部管理
适用场景 简单的定时数据同步、报表生成 复杂业务流程、多步骤编排、长耗时任务

关键结论：XXL-JOB 适合"到点执行一个动作"的简单场景；Temporal 适合"一个业务流程需要多个步骤、需要可靠保证、可能需要等待和人工介入"的复杂场景。两者不冲突，可以共存--简单定时任务用 XXL-JOB，复杂业务流程用 Temporal。

适用场景 简单的延迟通知、超时取消 复杂业务流程、多步骤编排

关键结论：MQ 延迟队列适合"延迟投递一条消息"的简单场景；Temporal 适合"延迟后还要执行一系列步骤"的复杂场景。用 MQ 做复杂流程编排，需要大量补偿代码，最终会退化成"手写版 Temporal"。

4.3 与 APISIX / 网关限流对比
!

定位差异：APISIX 是 API 网关，主要职责是路由、鉴权、限流等流量治理。Temporal 的限流是 Worker 级别的任务消费速率控制。两者不在同一层面，但在"保护下游接口"场景下有交集。

!

!
!
对比维度 APISIX 网关限流 Temporal Worker 限流
限流层级 HTTP 请求级别（网关层） 任务消费级别（Worker 层）
限流策略 QPS 限流 / 并发限流 / 令牌桶 Worker 全局并发数 + 每秒任务数
超限行为 直接返回 429 拒绝 任务在队列排队，不丢失不拒绝
排队缓冲 不支持（超出即拒绝） Task Queue 天然排队缓冲
重试机制 需客户端自行重试 引擎自动指数退避重试
状态管理 无状态 完整的 Workflow 状态管理
适用场景 保护 HTTP 接口不被瞬时流量打垮 保护下游 API + 保证任务可靠执行

关键结论：APISIX 解决的是"流量入口的限流"问题，超限即拒绝；Temporal 解决的是"任务执行的可靠性"问题，超限则排队，且保证最终一定执行。对于批量门禁下发这种必须全部执行成功、不能拒绝丢弃的场景，Temporal 的排队+重试模式远优于网关的拒绝模式。

5.4 运维与发布架构优势
!

基于“控制面与数据面分离”的架构设计，Temporal 在生产环境运维和业务迭代上具备传统单体/微服务架构难以比拟的优势：

!

1. Temporal Server 一次部署，长期稳定
!

Temporal Server 作为核心调度引擎，其职责是维护任务队列、持久化事件、分发任务。一旦部署完成并稳定运行，Temporal Server 本身不需要随业务迭代而频繁升级或重启。

!

  • 稳定性：Temporal Server 是纯粹的基础设施组件，不包含任何业务逻辑，变更频率极低，确保了核心调度层的高可用性。
  • 风险隔离：业务功能的新增、修改、迭代均不会波及 Temporal Server，即使业务代码出现问题，也不会导致调度系统崩溃。
    • !

2. 业务逻辑独立发布（Worker 驱动）
!

所有业务逻辑（Workflow 定义、Activity 实现）均运行在独立的 Worker 进程中。业务迭代和功能更新完全转化为 Worker 代码的发布与更新。

!

  • Jenkins 驱动发布：可以通过 Jenkins 独立构建和部署 Worker 集群。当需要新增业务场景（如增加新的审批流程）或修改现有逻辑时，只需编写/修改对应的 Worker 代码，打包后滚动更新 Worker 节点即可。
  • 零宕机更新：Temporal 支持 Workflow 的“版本控制（Versioning）”机制。当 Worker 更新时：
    • 新启动的 Workflow 会立即由新版本的 Worker 接管执行。
    • 正在执行中的老 Workflow，Temporal 引擎会确保其继续由旧版本（或兼容版本）的 Worker 处理，直到流程结束。
    • 整个过程完全无感，不需要停机维护，也不会导致正在进行的业务流程中断或数据丢失。
      • !
    • !

3. 故障隔离与弹性伸缩
!

  • Worker 崩溃不影响全局：单个 Worker 进程的崩溃只会影响其正在执行的少量任务，Temporal 会自动将这些任务重新分配给其他健康的 Worker，其他正在运行的 Workflow 不受影响。
  • 按需弹性扩容：在业务高峰期（如批量门禁下发），只需通过 Jenkins 或手动快速启动新的 Worker 实例，即可瞬间提升处理能力。流量回落时，可随时缩减 Worker 实例数量，实现资源的动态最优利用。
    • !

6.3 Worker 扩缩容机制
!

Temporal 的任务调度采用**长轮询（Long-Polling）**机制，Worker 的横向扩容极其简单：

!

  1. 解耦与缓冲：业务系统瞬间涌入大批请求时，任务存入 Task Queue 排队，即使 Worker 不足也不会丢失或崩溃
  2. 无状态平滑扩容：Worker 完全无状态，发现积压时只需启动更多 Worker 容器
  3. 即插即用：新 Worker 只需指定 Server 地址和 Task Queue 名称，自动连上领走任务，无需在 Server 上做任何配置

10.1 Java/JVM 相关
!

!
术语 补充说明
OOM（Out Of Memory） 内存溢出错误。当 Java 程序申请的内存超过 JVM（Java 虚拟机）可用堆内存时抛出的致命错误，会导致应用崩溃重启。本文中海康 4 万人批量调用时大量 HTTP 请求对象堆积在内存中，就可能引发 OOM。
JVM 堆（JVM Heap） Java 虚拟机管理的内存区域，用于存放程序运行期间创建的对象实例。堆内存不足时会触发垃圾回收（GC），频繁 GC 会导致应用响应变慢，最终可能 OOM。
GC（Garbage Collection，垃圾回收） Java 虚拟机自动回收不再使用的对象所占内存的机制。当内存中积压大量未完成的请求对象时，GC 会频繁触发，导致 CPU 占用升高、应用卡顿。
@Async Spring 框架提供的注解，标注后方法会在独立的线程池中异步执行，不阻塞主线程。但如果线程池容量不足且任务积压过多，反而会导致内存溢出。
Future Java 中代表"异步计算结果"的对象。发起异步调用后立即返回一个 Future，后续通过它获取最终结果。大量未完成的 Future 会持续占用内存。
CallerRunsPolicy Java 线程池的一种拒绝策略。当线程池队列满了之后，新任务不再被拒绝，而是由提交任务的线程（通常是主线程）自己执行。这会导致主线程被阻塞，影响整体响应。

10.2 接口与通信相关
!

!
术语 补充说明
API（Application Programming Interface） 应用程序编程接口，不同系统之间交互的约定。本文中"海康 API""门禁 API"指调用对应系统功能的 HTTP 接口。
REST（Representational State Transfer） 一种轻量级的 Web 服务接口风格，使用 HTTP 协议传输 JSON 格式数据，是目前最主流的 API 交互方式。
SOAP（Simple Object Access Protocol） 一种较重的 Web 服务协议，使用 XML 格式封装数据，通常用于企业级系统集成。本文中 BPM 流程引擎使用 SOAP 协议。
gRPC Google 开源的高性能远程调用框架，基于 HTTP/2 和 Protobuf 序列化协议。Temporal 主服务与 Worker 之间通过 gRPC 通信，调用延迟极低（< 5ms）。
Webhook 一种"反向 API"机制--不是主系统主动去查询结果，而是任务完成后主动 HTTP 回调通知主系统。类似快递员送完快递后给你发短信通知。
429 限流 HTTP 状态码 429 表示"请求过多"（Too Many Requests）。当调用方请求频率超过接口提供方的承受能力时，对方会返回 429 拒绝服务。
Base64 编码 一种将二进制数据（如人脸图片）转换为纯文本字符串的编码方式，便于通过 HTTP 接口传输。但编码后体积会增大约 33%，增加网络传输和内存开销。
3DES 加密 一种对称加密算法（Triple DES），是 DES 的增强版。但由于已存在安全漏洞，业界已不推荐使用，建议升级为 AES-256。本文中新开普门禁接口使用 3DES 加密。
OAuth2 一种授权框架，允许第三方应用在用户授权下访问其资源，而不需要暴露用户密码。本文中 EHR 系统使用 OAuth2 的 client_credentials 模式获取访问令牌（Token）。
Token（令牌） 身份验证凭证，类似"临时通行证"。客户端获取 Token 后，在后续请求中携带 Token 证明身份，无需每次传输用户名密码。
连接池 预先创建一组网络连接并复用的机制，避免每次请求都新建/销毁连接的开销。本文中 HttpWS 工具没有使用连接池，每次 SOAP 调用都新建连接，性能较差。

10.3 数据库与中间件相关
!

!
术语 补充说明
DB 慢查询 数据库中执行时间过长的 SQL 查询。高频定时扫库（如每 30 分钟全表扫描）会产生慢查询，占用数据库资源，影响其他正常业务查询。
Redis 一种内存级键值缓存数据库，读写速度极快。本文中用于缓存 SSO 登录 Token 和消息发送状态。
TTL（Time To Live，生存时间） 数据在缓存/消息队列中的存活时间，过期后自动删除。MQ 延迟队列的消息有 TTL 限制，而 Temporal 的持久化定时器无 TTL 限制。
死信队列（Dead Letter Queue） 消息队列中处理失败的消息会被自动转入的特殊队列，用于后续人工或自动处理。类似快递公司的"异常件仓库"。

10.4 架构与设计模式相关
!

!
术语 补充说明
Event Sourcing（事件溯源） 一种数据持久化模式：不存储最终状态，而是存储每一次状态变更事件（Event）。回放事件即可重建完整状态。Temporal 用此模式实现断点续传--Worker 崩溃后，从事件历史中恢复到崩溃前的进度继续执行。
Happy Path（快乐路径） 程序在一切正常、没有异常情况下的执行路径。Temporal 的理念是让开发者只写正常流程代码，异常处理由引擎自动兜底。
幂等（Idempotency） 同一操作执行一次和执行多次产生相同结果。例如"设置门禁权限为开启"是幂等的（重复设置无副作用），而"增加一条记录"不是幂等的（重复执行会产生多条）。
补偿（Compensation） 当某个步骤失败后，执行一个"反向操作"来撤销已完成步骤的影响。例如"下发权限"失败后，执行"撤销已下发的权限"。
状态机（State Machine） 描述业务对象在不同状态之间转换的模型。例如访客审批的状态流转：待审批 -> 审批中 -> 已通过 -> 权限已下发。
BFF（Backend For Frontend） 专为前端服务的后端中间层。前端不直接调用底层 API，而是通过 BFF 间接访问，BFF 负责数据格式转换、权限校验、聚合等。
RBAC（Role-Based Access Control，基于角色的访问控制） 一种权限管理模型：用户被分配角色，角色拥有权限，用户通过角色间接获得权限。如"管理员"角色可以终止工作流，"访客"角色只能查看。
控制面/数据面分离 控制面负责调度和管理（Temporal Server），数据面负责实际业务执行（Worker 集群）。两者独立部署互不影响，类似于"指挥所"与"作战部队"分离。
长轮询（Long-Polling） Worker 主动向 Server 拉取任务的机制：Worker 发送请求后，如果没有任务，Server 会保持连接等待，直到有任务或超时才返回。避免了频繁轮询的无效请求。
HPA（Horizontal Pod Autoscaler，水平自动扩缩容） Kubernetes 的自动扩缩容机制，根据 CPU/内存或自定义指标（如队列积压量）自动增加或减少 Worker 实例数量。

10.5 Temporal 核心概念
!

!
术语 补充说明
Workflow（工作流） Temporal 中一个完整的业务流程实例。由开发者用普通 Java 代码编写，定义了多个步骤的执行顺序。流程状态由引擎持久化，崩溃后可恢复。
Activity（活动） Workflow 中的一个具体执行步骤，通常是调用外部 API 或操作数据库的代码单元。Activity 失败后由引擎自动重试。
Worker（工作进程） 运行在独立服务器上的进程，负责实际执行 Workflow 和 Activity 代码。Worker 无状态，可随时增减实现扩缩容。
Task Queue（任务队列） Workflow 和 Activity 任务的缓冲队列。主系统提交任务到队列，Worker 从队列拉取任务执行。即使 Worker 不足，任务也在队列中排队等待，不会丢失。
Signal（信号） 外部系统向正在运行的 Workflow 发送的消息。可用于动态改期、取消、人工审批通过等场景。类似于给正在执行的任务"发送一条指令"。
RetryPolicy（重试策略） 配置 Activity 失败后的重试行为：最大重试次数、初始间隔、退避系数（Backoff Coefficient）、最大间隔。引擎按策略自动执行重试，开发者无需写重试代码。
指数退避（Exponential Backoff） 一种重试策略：每次重试的等待时间按指数增长（如 1s -> 2s -> 4s -> 8s），避免短时间内大量重试冲击下游接口。
Heartbeat（心跳） Worker 在执行长时间 Activity 时定期向 Server 汇报"我还活着"的信号。如果心跳中断，Server 可判断 Worker 宕机并重新调度任务。
Codec Server Temporal 的数据编解码服务，用于在 Web UI 展示前对加密的 Workflow Payload 进行解密，确保敏感数据不会明文暴露。
KMS（Key Management Service，密钥管理服务） 集中管理加密密钥的服务，提供密钥的创建、存储、轮换、审计等能力，比硬编码密钥更安全。
版本控制（Versioning） Temporal 用于实现 Workflow 代码平滑升级的机制。通过 Workflow.getVersion API，开发者可以在不中断正在运行的 Workflow 实例的情况下，引入新逻辑或修改旧逻辑。旧 Workflow 保持旧版本逻辑继续执行，新 Workflow 使用新版本逻辑，确保了向后兼容性和零宕机更新。
滚动更新（Rolling Update） 一种逐步替换旧版本实例为新版本实例的部署策略。Temporal Worker 集群的滚动更新允许在不停服的情况下，逐个或分批地用新版本 Worker 替换旧版本 Worker，新任务由新版本处理，老任务由旧版本继续处理直至完成，实现无缝过渡。

10.6 调度与并发相关
!

!
术语 补充说明
XXL-JOB 一个分布式定时任务调度平台，通过配置 Cron 表达式定时触发任务。适合简单的"到点执行一个动作"场景，但不支持多步骤编排和断点续传。
Cron 表达式 一种时间表达式，用于定义定时任务的触发时间。如 0 */5 * * * ? 表示每 5 分钟执行一次。
Quartz 另一个 Java 定时任务调度框架，功能与 XXL-JOB 类似，通过 Cron 表达式定时触发。
Semaphore（信号量） Java 并发编程中用于限制同时访问某资源的线程数量的机制。如 Semaphore(15) 表示最多允许 15 个线程同时执行。本文中需要手写信号量来限制 API 调用速率。
限流（Rate Limiting） 控制请求发送速率的机制，防止短时间大量请求打垮下游接口。类似于"水龙头限流"--控制出水量防止水花四溅。
削峰（Peak Shaving） 将瞬时高峰请求平滑分散到更长时间段处理，避免峰值压力。Temporal 的 Task Queue 天然实现削峰：高峰时排队，Worker 以恒定速率消费。
