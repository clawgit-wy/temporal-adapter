## 一、 核心实现原理：代码怎么写？

Temporal 提供了 `Workflow.sleep()` 函数。它的特别之处在于：**它是持久化的（Durable）**。

### 1. 业务逻辑流程

假设现在是下午 2:00，访客预约了 5:00 入场，要求 4:50 生效：

```
2:00 PM (客户端发起 Workflow) 
   │
   ▼
 计算等待时间: 4:50 PM - 2:00 PM = 2小时50分钟
   │
   ▼
【Workflow.sleep(2小时50分钟)】<-- 期间 Worker/Server 零 CPU、零内存占用
   │
   ▼ (到了 4:50 PM，Temporal 自动唤醒 Workflow)
   │
 执行 Activity: 调用门禁 API 开通权限
   │
   ▼
 4:50 PM 权限准时生效！

```

### 2. 代码示例 (Java)

```java
public class VisitorAccessWorkflowImpl implements VisitorAccessWorkflow {

    private final DoorAccessActivities doorActivities = Workflow.newActivityStub(
        DoorAccessActivities.class,
        ActivityOptions.newBuilder()
            .setStartToCloseTimeout(Duration.ofSeconds(30))
            .setRetryOptions(RetryOptions.newBuilder().setMaximumAttempts(5).build())
            .build()
    );

    @Override
    public void scheduleAccess(VisitorReservation reservation) {
        // 1. 计算需要等待的目标时间（下午 4:50）
        Instant effectiveTime = reservation.getAppointmentTime().minus(Duration.ofMinutes(10));
        Instant now = Instant.ofEpochMilli(Workflow.currentTimeMillis());

        // 2. 如果当前还没到 4:50，就进行定时等待
        if (effectiveTime.isAfter(now)) {
            Duration delay = Duration.between(now, effectiveTime);
            
            // 核心关键点：让工作流在此处挂起/休眠指定的时长
            Workflow.sleep(delay);
        }

        // 3. 时间一到（4:50 PM），Temporal 自动唤醒代码，执行真正的下发 Activity
        doorActivities.grantAccess(
            reservation.getVisitorId(), 
            reservation.getDoorIds()
        );
    }
}

```

## 二、 为什么 Temporal 做定时任务比传统方案强得多？

如果用传统的 **定时任务（XXL-JOB/Quartz）** 或 **MQ 延迟消息** 做这个需求，你会遇到很多痛点，而 Temporal 把它们全解决了：

### 1. 极高的精确度与稳定性

* **传统定时任务：** 需要写个扫库 Cron Job（比如每分钟扫一次 `status=PENDING` 且 `time <= 4:50` 的单子）。当预约单量大时，扫库容易产生 DB 慢查询甚至漏单。
* **Temporal：** 内部基于高效的时间轮（Timing Wheel）算法。定时器精确到毫秒级，到了 4:50 会精确唤醒任务。

### 2. 休眠期间“零资源占用”与“无限长等待”

* 传统线程池如果 `Thread.sleep()`，会白白占用内存和线程。
* 在 Temporal 中，当代码走到 `Workflow.sleep()` 时，**Worker 进程会将该工作流的状态安全地持久化到 Server 数据库，然后释放所有线程和内存**。即使这个 `sleep` 设为 30 天甚至 1 年，期间也**不消耗任何 CPU 和内存**。

### 3. 故障断电与重启保护（绝对不会漏下发）

* 假设在 **下午 3:30**（正处于休眠期）：
* 你的 Worker 进程崩溃重启了；
* 甚至 Temporal Server 服务器断电了。


* **结果：** 4:00 机器恢复上线后，Temporal 从数据库里读取定时器，发现“距离 4:50 还有 50 分钟”，**继续无缝倒计时**！到了 4:50 依旧会精准下发门禁，**绝无丢单风险**。

## 三、 进阶高级场景（Temporal 独有的灵活性）

在现实业务中，访客预约经常会发生变数，Temporal 处理这些动态变化极其方便：

### 场景 A：访客临时改期（例如改到 6:00 入场，要求 5:50 生效）

业务系统只需要向正在休眠的 Workflow 发送一个 **`Signal`（信号）**，改变目标时间，取消旧定时器并重新休眠即可：

```java
// 监听外部改期信号
@SignalMethod
public void updateAppointmentTime(Instant newTime) {
    this.appointmentTime = newTime;
    // 触发重新计算，中断当前的 sleep 并按新时间休眠
}

```

### 场景 B：访客取消预约

如果访客在 3:00 取消了预约，业务系统发送一个 `cancelSignal`，Workflow 收到后直接从 `sleep` 中醒来，结束流程，**后续的门禁下发 Activity 根本不会被触发**。
