# Temporal PoC 验证方案

> 本文档是 Temporal 引入的 **概念验证（Proof of Concept）** 执行手册，用于验证 Temporal 能否切实解决业务系统中的核心痛点。详细业务背景与解决方案说明参见 [Temporal业务应用方案介绍.md](file:///Users/apple/Desktop/AdapterService/docs/Temporal业务应用方案介绍.md)。

---

## 一、验证背景与目标

### 1.1 验证动因

当前宇通安保管理平台面临以下六大可靠性痛点，传统手写方案已难以继续维护：

| 痛点 | 典型场景 | 核心风险 |
| --- | --- | --- |
| 第三方接口被打垮（限流失控） | 海康人脸分组同步 4 万+ 人员、楼宇门禁 1000+ 人 × 500+ 设备 | 无速率限制，打垮海康/门禁接口 |
| 接口故障重试逻辑复杂（代码膨胀） | 30+ 外部系统集成点，仅 2 个有重试 | 失败即丢，数据不一致 |
| 多步骤编排与顺序依赖难以保证 | 楼宇门禁 17 个定时任务、入厂备案 6 个任务 | 前序失败后续仍执行 |
| 长耗时等待浪费资源（定时任务笨重） | 入厂备案每 30 分钟扫库、访客每分钟扫库 | DB 慢查询 + 漏单风险 |
| 异步结果通知不可靠（回调丢失） | 海康批量操作结果、BPM 审批结果 | 仅写日志，无主动回调 |
| 主服务内存溢出（OOM 风险） | 海康 4 万人全量分组更新 | 大量请求对象堆积 JVM |

### 1.2 验证目标

通过 5 个精心设计的 PoC 场景，验证 Temporal 的以下核心能力：

1. **内置限流**：Worker 级限流能否稳定保护下游接口不被打垮
2. **自动重试**：RetryPolicy 能否零代码实现指数退避重试
3. **断点续传**：Worker 崩溃后能否从断点恢复，不重跑已完成步骤
4. **持久化定时器**：`Workflow.sleep()` 能否精确替代扫库，休眠期间零资源占用
5. **可靠回调**：Webhook 回调失败后能否自动重试直到成功

### 1.3 场景选取依据

5 个验证场景均来源于 [Temporal迁移技术分析报告.md](file:///Users/apple/Desktop/AdapterService/docs/Temporal迁移技术分析报告.md) 中迁移评分 ≥ 17 的核心业务场景：

## 二、PoC 验证场景详情

### 场景一：海康批量同步与第三方接口削峰/限流（对应痛点一）

| 项目 | 内容 |
| --- | --- |
| **业务场景** | 海康人脸分组批量同步（迁移评分 24/25）：4 万+ 人员全量分组更新，逐人调用海康 Artemis SDK 单人 API；楼宇门禁权限批量下发（21/25）：1000+ 人 × 500+ 设备 = 50 万+ 次 API 调用 |
| **验证目标** | Temporal 是否能平滑限制调用 QPS，且任务绝不丢失 |
| **测试方案** | 配置 Worker 限流 `setMaxConcurrentActivityExecutionSize(15)` + `setMaxWorkerActivityTasksPerSecond(20)`，发起 1000 次 Activity 模拟批量下发 |
| **破坏性测试** | 观察是否以恒定 15 QPS 速率消费，不打垮 Mock 海康接口；对比当前 `@Async` 线程池（5-10 线程，无速率控制）的行为 |
| **预期结果** | 1000 个 Activity 平滑消费，Web UI 可见实时进度与成功率；**对比当前方案：无 OOM 风险，无限流失控** |

#### 本地代码骨架

```java
// 1. Activity 接口
@ActivityInterface
public interface HikBatchActivity {
    @ActivityMethod
    void syncPersonGroup(String personId, String groupId);
}

// 2. Activity 实现（用 sleep 模拟 50ms 接口耗时）
public class HikBatchActivityImpl implements HikBatchActivity {
    @Override
    public void syncPersonGroup(String personId, String groupId) {
        try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        // 实际环境中调用海康 Artemis SDK
        // hikArtemisClient.updatePersonGroup(personId, groupId);
    }
}

// 3. Workflow 定义
@WorkflowInterface
public interface HikBatchWorkflow {
    @WorkflowMethod
    void batchSyncPersonGroups(List<String> personIds, String groupId);
}

public class HikBatchWorkflowImpl implements HikBatchWorkflow {
    @Override
    public void batchSyncPersonGroups(List<String> personIds, String groupId) {
        HikBatchActivity activities = Workflow.newActivityStub(HikBatchActivity.class,
            ActivityOptions.newBuilder()
                .setStartToCloseTimeout(Duration.ofSeconds(10))
                .setRetryOptions(RetryOptions.newBuilder()
                    .setMaximumAttempts(3)
                    .setBackoffCoefficient(2.0)
                    .build())
                .build());

        for (String personId : personIds) {
            activities.syncPersonGroup(personId, groupId);
        }
    }
}

// 4. Worker 配置限流（核心验证点）
Worker worker = factory.newWorker("HIK_BATCH_TASK_QUEUE",
    WorkerOptions.newBuilder()
        .setMaxConcurrentActivityExecutionSize(15)  // 全局并发不超过 15
        .setMaxWorkerActivityTasksPerSecond(20)     // 每秒最多 20 个任务
        .build());
worker.registerWorkflowImplementationTypes(HikBatchWorkflowImpl.class);
worker.registerActivitiesImplementations(new HikBatchActivityImpl());
```

#### 验证操作步骤

1. 启动本地 Temporal 环境（参见第四章本地搭建指南）
2. 启动包含上述代码的 Worker 进程
3. 通过 Web UI 或 `tctl` 发起 Workflow，传入 1000 个人员 ID
4. 打开 Web UI 监控 Workflow 执行状态

**🧪 核心验证点：**
- 1000 个 Activity 是否以恒定 20 QPS 速率平滑消费，无瞬时高峰
- Web UI 实时进度条是否线性推进，无堆积或雪崩
- Worker 进程 CPU/内存是否稳定，无 OOM 风险

### 场景二：多系统接口故障与自动指数退避重试（对应痛点二）

| 项目 | 内容 |
| --- | --- |
| **业务场景** | BPM SOAP 接口（17/25）+ CRK 出入口权限下发（17/25）+ 海康 SDK（24/25），当前 30+ 集成点均无重试 |
| **验证目标** | RetryPolicy 能否自动重试不同类型接口（REST/SOAP），超过最大次数后能否优雅捕获 |
| **测试方案** | Activity 前 3 次故意抛异常，第 4 次才成功；配置 `setBackoffCoefficient(2.0)` |
| **破坏性测试** | 观察 Web UI 上的重试轨迹：1s -> 2s -> 4s 阶梯式重试 |
| **预期结果** | 第 4 次成功后 Workflow 继续，**业务系统无需写一行重试代码**；对比当前方案：30+ 集成点仅 2 个有重试 |

#### 本地代码骨架

```java
// Activity 实现：前 3 次失败，第 4 次成功
public class UnstableApiActivityImpl implements UnstableApiActivity {
    private final AtomicInteger counter = new AtomicInteger(0);

    @Override
    public String callExternalApi(String param) {
        int attempt = counter.incrementAndGet();
        if (attempt <= 3) {
            throw new RuntimeException("第三方接口 502 错误 (第 " + attempt + " 次)");
        }
        return "调用成功: " + param;
    }
}

// Workflow 配置 RetryPolicy（零重试代码）
public class RetryDemoWorkflowImpl implements RetryDemoWorkflow {
    @Override
    public void execute(String param) {
        UnstableApiActivity activities = Workflow.newActivityStub(UnstableApiActivity.class,
            ActivityOptions.newBuilder()
                .setStartToCloseTimeout(Duration.ofSeconds(5))
                .setRetryOptions(RetryOptions.newBuilder()
                    .setMaximumAttempts(5)
                    .setInitialInterval(Duration.ofSeconds(1))
                    .setBackoffCoefficient(2.0)    // 1s -> 2s -> 4s 指数退避
                    .setMaximumInterval(Duration.ofSeconds(30))
                    .build())
                .build());

        String result = activities.callExternalApi(param);
        // 第 4 次成功后继续执行，业务代码无任何重试逻辑
    }
}
```

#### 验证操作步骤

1. 启动 Worker 并发起 Workflow
2. 在 Web UI 上观察 Activity 的执行轨迹

**🧪 核心验证点：**
- Web UI Event History 中是否出现 3 次失败 + 1 次成功的记录
- 每次失败的重试间隔是否符合 1s → 2s → 4s 指数退避
- 第 4 次成功后 Workflow 是否自动继续，业务系统无感知

### 场景三：定时权限生效与长耗时等待（对应痛点四）

| 项目 | 内容 |
| --- | --- |
| **业务场景** | 入厂备案权限定时下发（23/25）：替代每 30 分钟扫库下发"当前时间+33分钟"数据；访客授权（22/25）：替代每分钟扫库前 10 分钟下发 |
| **验证目标** | `Workflow.sleep()` 能否精确替代扫库定时，长等待期间是否零 CPU/内存占用 |
| **测试方案** | Workflow 中计算等待至目标时间，调用 `Workflow.sleep(delay)` 进入休眠；模拟等待 10 分钟后自动唤醒执行权限下发 Activity |
| **破坏性测试** | 休眠期间查看 Worker CPU/内存（近乎为 0）；Kill Worker 后重启，验证定时器无缝继续倒计时 |
| **预期结果** | 精确到毫秒级定时唤醒，零资源占用，**对比当前方案：消除每 30 分钟扫库的 DB 慢查询和漏单风险** |

#### 本地代码骨架

```java
// 入厂备案权限定时下发：替代每 30 分钟扫库
public class EntryPermissionWorkflowImpl implements EntryPermissionWorkflow {
    @Override
    public void delegatePermission(String entryId, LocalDateTime appointmentTime, List<String> doorIds) {
        // 计算目标时间前 33 分钟的等待时长
        long delay = appointmentTime.minusMinutes(33)
            .atZone(ZoneId.systemDefault()).toInstant().toEpochMilli()
            - Workflow.currentTimeMillis();

        if (delay > 0) {
            Workflow.sleep(Duration.ofMillis(delay));  // 持久化定时器
        }

        EntryActivity activities = Workflow.newActivityStub(EntryActivity.class,
            ActivityOptions.newBuilder()
                .setStartToCloseTimeout(Duration.ofSeconds(30))
                .build());

        activities.delegatePermission(entryId, doorIds);
    }
}
```

#### 验证操作步骤

1. 发起 Workflow，设置 `appointmentTime` 为 5 分钟后的时间
2. Workflow 进入休眠状态
3. **💥 关键破坏性测试**：休眠 1 分钟后 Kill Worker 进程，10 秒后重启
4. 观察 Workflow 能否从断点继续倒计时

**🧪 核心验证点：**
- 休眠期间 Worker CPU 是否接近 0%，内存无明显增长
- Kill Worker 重启后，Workflow 是否无缝继续倒计时（不从头开始）
- 定时唤醒精度是否在毫秒级

### 场景四：多步骤编排与 Worker 崩溃断点续传（对应痛点三）

| 项目 | 内容 |
| --- | --- |
| **业务场景** | 楼宇门禁权限管理（21/25）：17 个定时任务存在顺序依赖（设备同步 -> 权限更新 -> 出入记录 -> 长期未进出 -> 代办发送） |
| **验证目标** | 多步骤 Workflow 能否保证顺序执行；机器恢复后是否从断点处接管，而非从头重跑 |
| **测试方案** | 3 个 Activity 顺序执行（模拟：更新设备 -> 下发权限 -> 发送代办），在第 2 步执行时强行 Kill Worker 进程，10 秒后重启 |
| **破坏性测试** | 观察 Web UI：第 1 个 Activity 不重新执行，从第 2 个继续；对比当前方案：XXL-JOB 前序失败后续仍执行 |
| **预期结果** | 自动断点续传，已完成的步骤绝不重复执行；**顺序依赖由 Workflow 代码天然保证，无需 cron 编排** |

#### 本地代码骨架

```java
// 多步骤编排：步骤顺序即执行顺序
public class BuildPowerWorkflowImpl implements BuildPowerWorkflow {
    @Override
    public void executeBuildPowerWorkflow(String date) {
        BuildActivity activities = Workflow.newActivityStub(BuildActivity.class,
            ActivityOptions.newBuilder()
                .setStartToCloseTimeout(Duration.ofSeconds(60))
                .setRetryOptions(RetryOptions.newBuilder()
                    .setMaximumAttempts(3)
                    .build())
                .build());

        // Step 1: 更新设备（完成后才执行 Step 2）
        activities.updateDeviceTask(date);
        Workflow.sleep(Duration.ofSeconds(5));  // 便于 Kill 进程

        // Step 2: 更新权限（依赖 Step 1 的设备数据）
        activities.updatePowerByDate(date);
        Workflow.sleep(Duration.ofSeconds(5));  // 便于 Kill 进程

        // Step 3: 发送代办
        activities.sendOwnerLongToDo(date);
    }
}
```

#### 验证操作步骤

1. 启动 Worker 并发起 Workflow
2. 在日志显示第 1 个 Activity 完成、第 2 个 Activity 正在执行时，**直接 Kill Worker 进程**
3. 等待 10 秒后重新启动 Worker

**🧪 核心验证点：**
- Web UI Event History 显示：第 1 个 Activity 标记为 `Completed`，不重新执行
- Worker 重启后从第 2 个 Activity 继续执行，而非从第 1 个开始
- 3 个 Activity 的执行顺序严格按代码顺序，无错乱

### 场景五：结果通知与 Webhook 回调（全链路闭环）（对应痛点五）

| 项目 | 内容 |
| --- | --- |
| **业务场景** | 海康批量操作（4 万人同步）完成后，需将成功/失败汇总结果回传主业务系统；当前仅写日志，无主动回调 |
| **验证目标** | Webhook 回调的可靠性及结果提取 |
| **测试方案** | 最后一个 Activity 中通过 HTTP POST 发送结果到 Webhook 接口 |
| **破坏性测试** | Webhook 接收端故意抛异常（模拟主系统宕机） |
| **预期结果** | Worker 自动重试发送 Webhook，直到主系统恢复返回 200；**对比当前方案：当前无回调机制，需人工查日志** |

#### 本地代码骨架

```java
// 1. Webhook 接收端（Spring Boot Controller）
@RestController
public class WebhookController {
    private final AtomicInteger failCounter = new AtomicInteger(0);

    @PostMapping("/api/webhook")
    public ResponseEntity<Map<String, Object>> receiveWebhook(@RequestBody Map<String, Object> payload) {
        int count = failCounter.incrementAndGet();
        if (count <= 3) {
            return ResponseEntity.status(500).body(Map.of("error", "模拟主系统宕机 (第 " + count + " 次)"));
        }
        return ResponseEntity.ok(Map.of("status", "ok", "received", payload));
    }
}

// 2. Workflow 最后一步发送 Webhook
public class WebhookNotifyWorkflowImpl implements WebhookNotifyWorkflow {
    @Override
    public void executeBatchWithWebhook(List<String> personIds, String groupId) {
        // ... 执行业务逻辑（批量同步）
        int successCount = personIds.size();
        int failCount = 0;

        // 最后一个 Activity：发送 Webhook
        WebhookActivity activities = Workflow.newActivityStub(WebhookActivity.class,
            ActivityOptions.newBuilder()
                .setStartToCloseTimeout(Duration.ofSeconds(10))
                .setRetryOptions(RetryOptions.newBuilder()
                    .setMaximumAttempts(10)
                    .setInitialInterval(Duration.ofSeconds(1))
                    .setBackoffCoefficient(2.0)
                    .build())
                .build());

        activities.sendBatchResult(Map.of(
            "successCount", successCount,
            "failCount", failCount,
            "totalCount", personIds.size()
        ));
    }
}
```

#### 验证操作步骤

1. 启动 Webhook 接收端服务
2. 发起 Workflow，执行完成后发送 Webhook
3. Webhook 接收端前 3 次故意返回 500 错误

**🧪 核心验证点：**
- Worker 自动重试发送 Webhook（1s → 2s → 4s 指数退避）
- 第 4 次成功后不再重试
- Web UI Event History 清晰展示每次尝试结果

## 四、PoC 验收标准

每个场景测试完成后，应验证以下验收标准：

| 场景 | 验收标准 |
| --- | --- |
| **场景一：限流** | 1000 次 Activity 以恒定 QPS 消费，无瞬时高峰；Worker 内存稳定无 OOM |
| **场景二：重试** | Activity 失败后按 1s→2s→4s 指数退避重试，最终成功；Web UI 可见完整重试轨迹 |
| **场景三：定时** | `Workflow.sleep()` 精确到毫秒唤醒；休眠期间 Worker CPU 接近 0；Kill 重启后继续倒计时 |
| **场景四：断点续传** | Kill Worker 重启后从断点继续，已完成步骤不重复执行；顺序依赖严格保证 |
| **场景五：Webhook** | Webhook 接收端故障时自动重试，恢复后成功投递；Web UI 可见每次尝试记录 |
