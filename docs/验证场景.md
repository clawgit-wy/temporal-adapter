### 场景一：海量并发与第三方接口削峰/限流（核心业务场景）

* **业务原貌：** 500 人批量下发权限，每人涉及 270 个门禁设备，产生 **13.5 万次** 接口调用。第三方门禁 API 承载力有限，直接并发请求会打垮对方或触发 429 限流。
* **本地验证目标：** 验证 Temporal 是否能平滑限制调用 QPS，且任务绝不丢失。
* **本地测试方案：**
1. 写一个 `GrantDoorAccessActivity`，用 `Thread.sleep(50)` 模拟 50ms 的接口请求。
2. 在代码中配置 Worker 限流参数（如：设置 `setMaxWorkerActivityTasksPerSecond(20)`，限制每秒最多跑 20 次）。
3. 用一个 Workflow 循环发起 1000 次 Activity（模拟缩减版的批量任务）。


* **🧪 核心验证点：**
* 打开 Web UI，观察 1000 个 Activity 是否以极度平滑的速率（如 20 QPS）被依次消费，**没有冲垮 Mock 接口**。
* 在 Web UI 查看实时进度与成功率。



---

### 场景二：第三方接口故障与自动指数退避重试

* **业务原貌：** 某个供应商的门禁系统接口极不稳定，偶尔报 500 错误，或者网络超时（Timeout）。
* **本地验证目标：** 验证 Temporal 的 `RetryPolicy` 能否自动重试，以及超过最大次数后能否优雅捕获。
* **本地测试方案：**
1. 在 Activity 代码里写一个计数器：前 3 次调用故意 `throw new RuntimeException("第三方接口 502 错误")`，第 4 次才成功。
2. 给 Activity 配置重试策略：`setBackoffCoefficient(2.0)`，初始间隔 1 秒。


* **🧪 核心验证点：**
* 在 Web UI 上观察该 Activity：会发现它自动进行了 **1s $\rightarrow$ 2s $\rightarrow$ 4s** 的阶梯式重试。
* 第 4 次重试成功后，Workflow 继续往下走，**整个过程业务系统无需写一行重试和逻辑捕捉代码**。



---

### 场景三：Worker 崩溃/服务器断电（断点续传与高可用）

* **业务原貌：** 一个涉及多个步骤的长流程正在跑（如：Step 1 扣款 $\rightarrow$ Step 2 下发门禁 $\rightarrow$ Step 3 发短信），跑第 2 步时，运行 Worker 的服务器突然断电宕机。
* **本地验证目标：** 验证机器崩溃恢复后，Temporal 是否能从**断点处接管**，而不是从头重新跑。
* **本地测试方案：**
1. 编写一个包含 3 个 Activity（按顺序执行）的 Workflow，每个 Activity 间加上 5 秒延迟。
2. 启动 Worker 并发起 Workflow。
3. **💥 关键破坏性测试：** 在日志显示第 1 个 Activity 完成、第 2 个正在执行时，**直接强行 Kill 掉你的 Worker 进程（或在终端按 `Ctrl + C`）**。
4. 等待 10 秒后，重新启动 Worker 进程。


* **🧪 核心验证点：**
* 重新启动 Worker 后，观察 Web UI：第 1 个 Activity **不会重新执行**，Temporal 自动从第 2 个未完成的 Activity 继续往下跑！



---

### 场景四：长耗时等待与异步回调（Human-in-the-Loop）

* **业务原貌：** 某个权限下发流程需要主管人工审批（可能等 2 小时甚至 3 天），或者需要定时在 30 分钟后自动关锁。
* **本地验证目标：** 验证长等待期间是否**零 CPU/内存占用**，以及能否通过 `Signal` 唤醒。
* **本地测试方案：**
1. 在 Workflow 代码中写一个 `Workflow.await(() -> isApproved)` 或 `Workflow.sleep(Duration.ofMinutes(10))`。
2. 发起 Workflow，使其进入 `Running (Waiting)` 状态。


* **🧪 核心验证点：**
* 在等待阶段，查看 Worker 进程的 CPU/内存，处于彻底挂起状态，占用几乎为 0。
* 尝试在 Temporal Web UI 上找到这个 Workflow，通过界面手动给它发送一个叫 `approveSignal` 的 Signal（信号），观察 Workflow **瞬间被唤醒继续向下执行**。



---

### 场景五：结果通知与 Webhook 回调（全链路闭环）

* **业务原貌：** Worker 执行完复杂的批量任务后，需要将最终的成功/失败汇总结果回传给主业务系统。
* **本地验证目标：** 验证 Webhook 回调的可靠性及结果提取。
* **本地测试方案：**
1. 使用 Spring Boot 写一个极简的 Webhook 接收 Controller：`@PostMapping("/api/webhook")`。
2. 在 Workflow 的最后一个 Activity 中，把整个 Workflow 的执行结果（如：`{successCount: 498, failCount: 2}`）通过 HTTP POST 发送到这个 Webhook 接口。


* **🧪 核心验证点：**
* 验证主业务系统能否顺利拿到带有完整的 Payload 数据的通知。
* 尝试在 Webhook 接收端故意抛异常（模拟主系统宕机），验证 Worker 会自动重试发送 Webhook，直到主系统恢复并返回 200。

为了用最快的方式在本地跑通上述 5 个场景，建议按照以下步骤搭建测试环境：

1. **环境一键拉起：** 本地安装 Docker，使用官方的 `docker-compose.yml` 一键启动 **Temporal Server + PostgreSQL + Web UI**：
* 运行成功后，直接访问 `http://localhost:8088` 查看 Web UI 控制台。


2. **应用集成：** 在你现有的 Java / Spring Boot 项目中引入 `temporal-sdk` 依赖，新建一个 `benchmark` 模块专门写上述场景的测试代码。
3. **单机验证：** 在本地 IDE 里启动你的 Spring Boot 应用（即启动了 Worker），就可以开始按上面的场景逐一压测和做破坏性验证了！
