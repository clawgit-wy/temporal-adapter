# 楼宇门禁权限下发业务逻辑文档

## 1. 概述

本文档基于 safety-service-master（后端）和 safety-web-master（前端）项目分析整理，描述楼宇门禁权限下发的完整业务逻辑，作为 device-access-worker 工作流设计的业务依据。

## 3. 访客权限下发流程

### 3.1 状态机

| 状态值 | 状态名 | 说明 |
|--------|--------|------|
| 0 | 未发卡 | EIP审批通过后的初始状态 |
| 1 | 已发卡 | 权限下发成功 |
| 2 | 已退卡 | 退卡操作完成 |
| 3 | 审批中 | Web端提交后 |
| 4 | 超时关闭 | EIP超时 |
| 5 | 未到访 | EIP流程检查 |
| 6 | 驳回 | EIP驳回 |
| 7 | 废弃 | EIP废弃 |
| 8 | 已进厂 | Kafka消息更新 |
| 9 | 已出厂 | Kafka消息更新 |
| 10 | 滞留 | 定时任务更新 |
| 11 | 权限已下发 | 门卫手动下发时使用 |

### 3.2 权限下发触发方式

#### 方式一：EIP审批通过后自动下发

```
EIP回调(RELEASE状态)
  -> 查询访客列表
  -> 查询绝密区
  -> 黑名单过滤
  -> 遍历每条访客记录:
    -> 获取被访人员员工号(LDAP查询)
    -> 判断是否自动下发:
       条件1: EIP状态为RELEASE(30)
       条件2: 访客有照片
       条件3: 访客开关为开
       条件4: 当前时间+40分钟 >= 入厂开始时间
    -> 调用 sendCard() 下发权限
  -> 更新数据库
  -> 未退卡检查
```

#### 方式二：定时任务自动下发

```
定时任务
  -> 更新滞留状态
  -> 查询待下发数据:
     条件: vendorState=0, now <= startTime <= now+40min
  -> 过滤无照片记录
  -> 黑名单过滤
  -> 遍历下发
  -> 批量更新状态
```

#### 方式三：门卫手动下发（单条/批量）

```
门卫PC操作
  -> Token校验获取门卫信息
  -> 查询访客记录
  -> 校验: 未超过入厂结束时间
  -> 校验: 访客请求厂区非空
  -> 校验: 门卫拥有权限厂区非空
  -> 调用 sendCardByHand() 下发
```

### 3.3 核心下发逻辑（sendCard）

```
输入: 访客记录, 涉密厂区Map, 黑名单列表

Step 1: 涉密厂区处理
  -> 将 factoryId 复制到 issueFactory
  -> 如果涉密(secretState==1):
     -> 从 secretRegion 提取涉密厂区编码
     -> 将涉密厂区从 issueFactory 移除, 加入 unIssueFactory

Step 2: 厂区空值校验
  -> issueFactory 为空则跳过下发

Step 3: 黑名单过滤
  -> 黑名单入厂申请为空列表 -> issueFactory 置空
  -> 非空列表 -> 取访客请求厂区与黑名单申请厂区的交集

Step 4: 获取被访人员员工号
  -> 通过 LDAP 查询(姓名+手机号)
  -> 为空则标记异常, 不下发

Step 5: 注销旧卡
  -> 将同一卡号的已发卡数据全部置为已退卡状态

Step 6: 人脸下发
  -> 前提: photo 非空
  -> 合并同一访客多条记录的厂区权限(mergeParam)
  -> 再次处理涉密(dealSecret)
  -> 调用 CRK 接口下发人脸权限:
     - crosstype=0(人脸)
     - crossdata=照片Base64
     - stafftype=1(访客)
     - devnos=设备号数组
     - tcmid=访客卡A/B(根据有无身份证照片)

Step 7: 状态更新
  -> 成功: vendorState=1, 记录发卡时间
  -> 失败: vendorState不变, 标记异常
```

### 3.4 门卫手动下发差异（sendCardByHand）

| 对比项 | 自动下发(sendCard) | 门卫单条下发(sendCardByHand) | 门卫批量下发(sendCardByHandList) |
|--------|-------------------|---------------------------|-------------------------------|
| 厂区范围 | 访客请求的全部厂区 | 门卫管辖厂区 | 门卫管辖厂区 |
| 涉密厂区 | 排除 | **包含** | 排除 |
| 成功状态 | vendorState=1 | vendorState=11 | vendorState=11 |
| 厂区追加 | 否 | 是(在已下发基础上追加) | 是 |

### 3.5 合并下发逻辑（mergeParam）

同一访客（手机号+身份证号唯一标识）多条访客记录的合并规则：

| 字段 | 合并规则 |
|------|---------|
| factoryId | 去重合并 |
| issueFactory | 去重合并 |
| unIssueFactory | 去重合并 |
| secretRegion | 去重合并 |
| endTime | 取最大值 |
| secretState | 任一为1则为1 |
| idCardPhoto | 取第一条非空值 |

### 3.6 tcmid 双卡类型规则

```
有身份证照片(idCardPhoto非空且非默认值"T") -> visitorCardTcmIdB (访客卡B)
无身份证照片 -> visitorCardTcmIdA (访客卡A)
```

## 4. 员工权限下发流程

### 4.1 楼宇门禁申请流程

```
员工发起申请
  -> 判断角色类型(checkBuildRoleType)
     ├── roleType=1(员工) -> 普通申请表单
     └── roleType≠1 -> 科长/管理员流程
  -> 选择门禁(DoorAccessSelect组件)
  -> 批量获取门禁详情(listWithSecretBatch)
  -> 选择对接部门 + 设置申请期限 + 选择本部门科长
  -> 提交申请(saveAndCreateProcess)
  -> BPM流程审批(auditProcess)
     ├── 通过 -> 门禁权限开通
     ├── 不通过 -> 驳回
     └── 部分通过(partPassProcess) -> 仅部分门禁开通
```

### 4.2 员工人脸发行

```
获取员工门禁权限(getBuildDeviceId)
  -> 整理人脸下发数据(formatFaceIssueData)
  -> 获取设备:
     ├── 正式员工 -> empowerType="正式员工", regionName="大门人脸"
     └── 外协 -> empowerType="外协", regionName="大门人脸"
  -> 无人事信息 -> 先调用 sendToCrkEditStaff() 新增
  -> 获取厂区权限(getIssueFactory)
  -> 获取授权设备(getEmpowerDevices)
  -> 合并楼宇门禁设备权限
  -> 调用 modifyFaceForOne() 执行人脸改写
```

## 5. 权限注销/退卡流程

### 5.1 访客权限注销

```
注销请求(cancelPermissionByPerson)
  -> 状态校验: vendorState in {1,8,9,5,11}
  -> 设置 inFactoryProcess="注销", vendorState=2
  -> 注销人脸: sendDataRecord(crosstype="0", endDate=当前时间)
  -> 注销二维码: sendDataRecord(crosstype="1", endDate=当前时间)
  -> 更新数据库
```

### 5.2 退卡注销（hairpinNoBack）

```
Step 1: 查询卡号
  -> 调用 CRK: /api/Staff/GetByFunc (根据手机号查询Reserve2即卡号)

Step 2: 注销人脸
  -> 对3个固定GID分别调用: /api/TokenService/Unregister
  -> 请求体: { SubSystems:[2], TokenType:1, TokenOper:12, Token:手机号, Gid:GID, ProjectGids:[GID] }

Step 3: 注销卡(如有卡号)
  -> 对3个GID再次调用注销接口注销卡

3个GID:
  - 8A0ADE28-...
  - FF7F139D-...
  - 35EC9884-...
```

### 5.3 定时关闭访客权限

```
场景: 访客有多条有效访客记录, 某条过期需关闭, 但不能影响其他未过期记录

Step 1: 查询过期数据(当前时间前33分钟到当前时间)
Step 2: 按访客(手机号+身份证号)分组
Step 3: 关闭过期权限
  -> 合并所有厂区权限
  -> 调用 sendDataRecord(crosstype="0", endDate=当前时间-33分钟) 关闭权限
Step 4: 开通未过期权限
  -> 合并未过期记录的厂区权限
  -> endTime取最大值
  -> 调用 sendDataRecord(crosstype="0") 重新下发有效权限
```

## 6. 关键业务规则

### 6.1 时间规则

| 规则 | 说明 |
|------|------|
| 40分钟规则 | 入厂开始时间前40分钟才允许自动下发权限 |
| 33分钟规则 | 定时关闭权限时查询窗口为当前时间前33分钟 |
| 35秒有效期 | 二维码有效期为35秒 |

### 6.2 权限规则

| 规则 | 说明 |
|------|------|
| 涉密厂区排除 | 自动下发排除涉密厂区，门卫手动单条下发包含涉密厂区 |
| 黑名单时间交集 | 黑名单访客取申请时间段与黑名单入厂申请时间段有交集的厂区 |
| 合并下发 | 同一访客多条记录合并厂区权限后一次性下发 |
| 门卫权限限制 | 门卫只能下发自己所辖厂区的权限 |
| 退卡前置 | 每次发卡前先注销同一卡号的已发卡未退卡数据 |
| 手机号前缀 | 下发时手机号加"F"前缀 |

### 6.3 tcmid 双卡类型

| 条件 | tcmid | 说明 |
|------|-------|------|
| 有身份证照片 | visitorCardTcmIdB | 访客卡B |
| 无身份证照片 | visitorCardTcmIdA | 访客卡A |
| 默认值"T" | visitorCardTcmIdB | 标记"无实际身份证但按有身份证下发" |

## 7. CRK 出入口接口调用规范

### 7.1 人脸/卡下发接口

- **URL**: `${sendData.qrUrl}`
- **Method**: POST
- **请求体**:

```json
{
  "phone": "F18928969687",    // 手机号加F前缀
  "idno": "420881...",         // 身份证号
  "staffname": "访客姓名",
  "devnos": [3, 4, 311],       // 设备号数组
  "crosstype": "0",            // 0=人脸, 1=二维码, 2=门禁卡
  "crossdata": "Base64照片",   // 人脸=照片Base64, 门禁=卡号
  "stafftype": "1",            // 1=访客
  "tcmid": "访客卡A/B",
  "endtime": "2024-09-20 23:59:59"
}
```

### 7.2 注销接口

- **URL**: `${crk.Unregister.url}` (`/api/TokenService/Unregister`)
- **Method**: POST
- **请求体**:

```json
{
  "SubSystems": [2],
  "TokenType": 1,
  "TokenOper": 12,
  "Token": "18928969687",
  "Redate": "2024-09-20",
  "Gid": "8A0ADE28-...",
  "ProjectGids": ["8A0ADE28-..."],
  "Remark": "访客接口操作员"
}
```

### 7.3 查询卡号接口

- **URL**: `${crk.GetByFunc.url}` (`/api/Staff/GetByFunc`)
- **Method**: POST
- **用途**: 根据手机号查询 Reserve2（卡号）

## 8. 设备授权查询逻辑

### 8.1 授权设备号查询

```
输入: factoryId(厂区ID, 分号分隔), regionId(区域ID), deviceType(设备类型), authFactory(门卫权限厂区)

1. factoryId 按分号拆分为多个工厂ID
2. authFactory 作为过滤器, 只选择门卫有权限的厂区
3. 查询 safety_empower_device 表:
   - delete_falg = false
   - factory_id IN (factoryList)
   - region_name LIKE '%deviceType%'
   - empower_type = '访客' / '正式员工' / '外协'
4. 设备号筛选:
   - regionId 非空:
     ├── 区域名含"大门" -> 直接纳入
     └── 其他 -> 仅当 regionId 包含设备对应的 regionId 时纳入
   - regionId 为空: 所有非空且非"/"的设备号纳入
5. 返回 int[] 设备号数组
```

### 8.2 设备类型与授权类型

| empowerType | regionName | 适用场景 |
|-------------|-----------|---------|
| 访客 | 大门人脸 | 访客人脸设备 |
| 正式员工 | 大门人脸 | 正式员工人脸设备 |
| 外协 | 大门人脸 | 外协人员人脸设备 |

## 9. 异常处理

### 9.1 下发失败处理

| 场景 | 处理方式 |
|------|---------|
| 人脸下发失败 | inFactoryProcess="异常", 清空 userId/issueFactory/unIssueFactory |
| 被访人查询失败 | inFactoryProcess="异常", 清空 userId |
| 厂区为空 | 记录日志跳过，不下发 |
| 超过入厂结束时间 | 抛出 BizException 或跳过 |

### 9.2 重试机制

| 场景 | 机制 |
|------|------|
| 手动重发 | 根据 sendState 判断失败类型, 重新调用 sendDataRecord |
| 定时任务重试 | 持续查询 vendorState=0 的未发卡数据重试 |
| Kafka首次进厂补发 | 首次进厂时按"有身份证"模式重新下发 |
| CRK接口 | **无自动重试**(原系统缺陷, Temporal工作流可解决) |

## 10. 工作流映射

基于以上业务逻辑，device-access-worker 项目的工作流设计如下：

| 工作流 | 对应业务场景 | 核心流程 |
|--------|------------|---------|
| PermissionIssueWorkflow | 员工/访客权限下发 | 校验 -> 注销旧卡 -> 人脸发行 -> 卡发行 -> 回调 |
| PermissionModifyWorkflow | 权限改写 | 校验 -> 人脸改写 -> 卡修改 -> 回调 |
| PermissionCancelWorkflow | 权限注销/退卡 | 查询卡号 -> 注销人脸(3个GID) -> 注销卡(3个GID) -> 回调 |
| PermissionIncrementWorkflow | 增量权限管理 | 人脸增量(增加/删除设备) -> 回调 |
| BatchPermissionIssueWorkflow | 批量权限下发 | 并发下发(校验->注销旧卡->人脸->卡) -> 合并结果 -> 回调 |
| VisitorPermissionIssueWorkflow | 访客权限下发(含合并逻辑) | 时间校验 -> 涉密过滤 -> 黑名单过滤 -> 合并下发 -> 回调 |
