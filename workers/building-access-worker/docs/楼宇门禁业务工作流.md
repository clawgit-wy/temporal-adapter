# 楼宇门禁业务工作流设计文档

> **项目**: building-access-worker
> **版本**: 1.0.0
> **更新日期**: 2026-08-13
> **适用范围**: 楼宇门禁权限下发、设备数据同步、权限全量初始化、人员变更权限确认 4 大业务工作流

---

## 1. 概述

building-access-worker 是基于 Temporal 工作流引擎构建的楼宇门禁业务编排服务，承担 safety-service-master 后端拆分后剥离出来的门禁业务编排职责。本服务对接富士（Fuji）与新开普（Xinkaipu）两套门禁设备系统，将原本散落在 safety-service-master Handler 层中的长链路、需要重试与限流的门禁业务流程，重构为可观测、可重试、可补偿的 Temporal Workflow。

### 1.1 四大业务工作流

| 序号 | 工作流 | 中文名称 | TaskQueue | 场景标识 | 并发/QPS |
|------|--------|----------|-----------|----------|----------|
| 1 | PermissionDistributionWorkflow | 大规模权限下发工作流 | PERMISSION_DISTRIBUTION_TASK_QUEUE | permissionDistribution | 并发 20 / QPS 20 |
| 2 | DeviceSyncWorkflow | 设备数据同步工作流 | DEVICE_SYNC_TASK_QUEUE | deviceSync | 并发 10 |
| 3 | PermissionInitWorkflow | 权限全量初始化工作流 | PERMISSION_INIT_TASK_QUEUE | permissionInit | 并发 15 |
| 4 | DepartConfirmWorkflow | 人员变更权限确认工作流 | DEPART_CONFIRM_TASK_QUEUE | departConfirm | 并发 15 |

### 1.2 设计目标

1. **解耦业务编排**：将门禁业务流程从 safety-service-master 中剥离，业务系统仅保留 CRUD 与 Webhook 接收，长链路编排下沉到 Worker。
2. **可观测可重试**：依托 Temporal 自带的 Activity 重试、超时、Signal/Query 能力，实现失败自动重试、人工干预、进度可查。
3. **限流保护**：通过 `WorkerOptions.setMaxWorkerActivitiesPerSecond` 在 Worker 层对富士/新开普接口做 QPS 限流，避免压垮第三方。
4. **多场景共存**：单 Worker 容器通过 `WORKER_SCENARIOS` 环境变量控制启动哪些场景，支持全量部署或按场景拆分实例。

## 2. 富士设备接口规范

富士设备 API 基础路径由配置项 `fuji.api.base-url` 控制，所有接口均为 HTTP POST，Content-Type 为 `application/json`。富士设备接口的设备类型标识为 `FUJI`。

### 接口1: 发行校验 (CheckTokenState)

- **路径**: `/Api/FaceHandSet/CheckTokenState`
- **用途**: 校验卡号/人脸是否已有发行信息
- **Client 方法**: `FujiApiClient.checkTokenState(CheckTokenRequest)`
- **Activity**: CheckTokenActivity

**请求参数 (CheckTokenRequest)**:

| 字段 | 类型 | 说明 |
|------|------|------| 
| TokenType | int | 0=卡, 1=人脸 |
| Token | String | TokenType=0 时传卡号, TokenType=1 时传 staffNo |

**响应参数 (CheckTokenResponse)**:

| 字段 | 类型 | 说明 |
|------|------|------|
| code | int | 200=存在发行信息, 500=不存在 |
| msg | String | 提示信息 |
| serverTime | String | 服务器时间 |
| result | Object | 发行详细信息（存在时返回） |

### 接口2: 人脸发行 (FaceIssue)

- **路径**: `/Api/FaceHandSet/FaceIssue`
- **用途**: 向设备下发人脸权限
- **Client 方法**: `FujiApiClient.faceIssue(FaceIssueRequest)`
- **Activity**: FaceIssueActivity

**请求参数 (FaceIssueRequest)**:

| 字段 | 类型 | 说明 |
|------|------|------|
| OperType | int | 0=发行 |
| Staff | StaffInfo | 人员信息 |
| BeginTime | String | 生效日期，如 `2025-09-10` |
| EndTime | String | 失效日期，如 `2034-11-06` |
| AuthorizeDeviceNo | List\<Integer\> | 授权设备编号列表 |
| ProjectGids | List\<String\> | 项目GID列表 |
| StaffState | int | 0=不变, 1=新增, 2=修改 |
| FacePicture | String | 人脸图片（Base64） |

**响应参数 (FaceIssueResponse)**:

| 字段 | 类型 | 说明 |
|------|------|------|
| code | int | 200=成功 |
| msg | String | 提示信息 |
| serverTime | String | 服务器时间 |
| result | Object | 发行结果 |

### 接口3: 人脸发行改写 (FaceModify)

- **路径**: `/Api/FaceHandSet/FaceModify`
- **用途**: 修改已发行的人脸权限（更换设备、调整有效期等）
- **Client 方法**: `FujiApiClient.faceModify(FaceIssueRequest)`
- **Activity**: FaceModifyActivity

**请求参数**: 同接口2，区别为 `OperType=1`（改写），`StaffState=2`（修改）。

### 接口4: 卡发行 (DoorIssue)

- **路径**: `/Api/FaceHandSet/DoorIssue`
- **用途**: 向门禁设备下发卡权限
- **Client 方法**: `FujiApiClient.cardIssue(CardIssueRequest)`
- **Activity**: CardIssueActivity

**请求参数 (CardIssueRequest)**:

| 字段 | 类型 | 说明 |
|------|------|------|
| useModel | int | 使用模式，如 1 |
| orginazitionId | String | 组织ID |
| staffNo | String | 人员编号 |
| tokenId | String | 卡号 |
| endDate | String | 失效日期 |
| tokenOper | int | 操作类型，如 1 |
| stcm | String | 子卡类型ID |
| tcm | String | 卡类型ID |
| serialNo | String | 序列号 |
| token | String | 卡号 |
| icStartTimeL1-L4 | String | 时段左边界1-4 |
| icStartTimeR1-R4 | String | 时段右边界1-4 |
| CarPass | String | 车辆通行密码 |
| beginDate | String | 生效日期 |
| staffName | String | 人员姓名 |
| tokenType | int | 令牌类型，如 1 |
| AuthDevice | List\<String\> | 授权设备列表 |

**响应参数 (CardIssueResponse)**: 同 FaceIssueResponse。

### 接口5: 人脸增量权限及删除 (FaceModifyBypowerType)

- **路径**: `/Api/FaceHandSet/FaceModifyBypowerType`
- **用途**: 增量管理设备权限（增加/删除指定设备）
- **Client 方法**: `FujiApiClient.faceModifyByPowerType(FaceIncrementRequest)`
- **Activity**: FaceIncrementActivity

**请求参数 (FaceIncrementRequest)**: 同接口2，增加以下字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| powerType | int | 0=增加设备权限, 1=删除设备权限 |

**说明**: 只对 `AuthorizeDeviceNo` 列表中的设备产生增量操作，不影响其他设备。

### 富士附加接口: 权限注销 (Unregister)

- **路径**: `/api/TokenService/Unregister`（默认值，可通过 `fuji.api.unregister-path` 配置）
- **用途**: 注销人脸/卡权限，需对 3 个固定 GID 分别调用
- **Client 方法**: `FujiApiClient.unregister(UnregisterRequest)`
- **Activity**: PermissionCancelActivity

**请求参数 (UnregisterRequest)**:

| 字段 | 类型 | 说明 |
|------|------|------|
| SubSystems | List\<Integer\> | 子系统列表，固定为 `[2]` |
| TokenType | int | 1=人脸, 0=卡 |
| TokenOper | int | 12=注销 |
| Token | String | 令牌值: 人脸时为手机号, 卡时为卡号 |
| Redate | String | 注销日期 |
| Gid | String | 项目GID |
| ProjectGids | List\<String\> | 项目GID列表 |
| Remark | String | 备注 |

### 富士附加接口: 按手机号查询卡号 (GetByFunc)

- **路径**: `/api/Staff/GetByFunc`（默认值，可通过 `fuji.api.get-by-func-path` 配置）
- **用途**: 退卡时查询访客的卡号（Reserve2 字段）
- **Client 方法**: `FujiApiClient.getByFunc(String phone)`
- **Activity**: PermissionCancelActivity.queryCardNo(String phone)

## 3. 新开普设备接口规范

新开普设备 API 基础路径由配置项 `xinkaipu.api.base-url` 控制，所有接口走 `IdentityWebService/Identity.ThirdOpenApiCall.ashx`，按 `group/{methodName}` 路由分发。新开普设备类型标识为 `XINKAIPU`。认证参数 `dpcode`、`appid` 由配置项提供，`encryption-key` 与 `signature-key` 用于 3DES + SHA256 加密签名（待按原 safety-service-master `BuildEncryptUtil` 协议实现）。

### 接口1: 获取门禁设备区域信息 (GetAccessTermAreaInfo)

- **路径**: `/IdentityWebService/Identity.ThirdOpenApiCall.ashx/group/GetAccessTermAreaInfo`
- **Client 方法**: `XinkaipuApiClient.getAccessTermAreaInfo()`
- **Activity**: DeviceSyncActivity.fetchDevicePage

**请求参数**: 仅公共认证参数（dpcode、appid）。

**响应参数**: 设备区域信息列表（含 deviceCode、deviceName、areaId、termId、termAddr 等字段）。

### 接口2: 获取门禁区域信息 (GetAccessAreaInfo)

- **路径**: `/IdentityWebService/Identity.ThirdOpenApiCall.ashx/group/GetAccessAreaInfo`
- **Client 方法**: `XinkaipuApiClient.getAccessAreaInfo()`
- **Activity**: DeviceSyncActivity（区域补全）

**请求参数**: 仅公共认证参数。

**响应参数**: 门禁区域信息列表（含 areaId、areaName、levf 等字段，levf: 1园区/2楼栋/3单元/4楼层/5房间）。

### 接口3: 门禁权限下发 (AddGrantByOutid)

- **路径**: `/IdentityWebService/Identity.ThirdOpenApiCall.ashx/group/AddGrantByOutid`
- **Client 方法**: `XinkaipuApiClient.addGrantByOutid(outid, extendIds, empcode, beginDate, endDate)`
- **Activity**: DeviceSyncActivity / 业务系统集成

**请求参数**:

| 字段 | 类型 | 说明 |
|------|------|------|
| dpcode | String | 认证参数 |
| appid | String | 认证参数 |
| outid | String | 人员外部ID（员工号） |
| extendids | List\<String\> | 设备编码列表 |
| empcode | String | 固定账号，默认 `mjqxdj` |
| begindate | String | 生效日期 |
| enddate | String | 失效日期 |

**分批策略**: 新开普授权设备按 **200 个/批** 分批授权，避免单次请求过大。

### 接口4: 查询授权信息 (GetGrantInfo)

- **路径**: `/IdentityWebService/Identity.ThirdOpenApiCall.ashx/group/GetGrantInfo`
- **Client 方法**: `XinkaipuApiClient.getGrantInfo(String outid)`
- **Activity**: PermissionQueryActivity

**请求参数**:

| 字段 | 类型 | 说明 |
|------|------|------|
| dpcode | String | 认证参数 |
| appid | String | 认证参数 |
| outid | String | 人员外部ID（员工号） |

**响应参数**: 该人员在新开普所有设备上的授权明细。

### 接口5: 查询进出记录 (GetRecordInfo)

- **路径**: `/IdentityWebService/Identity.ThirdOpenApiCall.ashx/group/GetRecordInfo`
- **Client 方法**: `XinkaipuApiClient.getRecordInfo(beginTime, endTime, outid)`

**请求参数**:

| 字段 | 类型 | 说明 |

### 4.2 大规模权限下发工作流 (PermissionDistributionWorkflow)

对应 BPM 审批通过后的批量权限下发场景，是 4 个工作流中最核心、链路最长的。支持 Signal 触发失败重试、Query 查询进度。

**流程图**:
     
```
开始
  │
  ├─ Step 1: 白名单校验 (ValidateActivity.filterWhitelistStaff)
  │    └─ 过滤非白名单人员（whitelist=true 时启用）
  │
  ├─ Step 2: 创建下发日志 (LogActivity.createIssueLogs)
  │    └─ 批量创建日志记录，返回 logId 列表
  │
  ├─ Step 3: 并行下发 (Async.function, 并发上限 maxConcurrency=20)
  │    │  每个人员执行:
  │    ├─ 3.1 发行校验 (CheckTokenActivity.checkToken)
  │    │    └─ TokenType=1, Token=staffNo
  │    │       ├─ code=200: 已有发行信息，继续
  │    │       └─ code=500: 无发行信息，继续首次发行
  │    ├─ 3.2 人脸发行 (FaceIssueActivity.issueFace)
  │    │    └─ OperType=0, StaffState=1
  │    └─ 3.3 卡发行 (CardIssueActivity.issueCard)
  │
  ├─ Step 4: 汇总结果 (Promise.get 收集所有人员结果)
  │    └─ 统计 successCount / failCount / failedStaffNos
  │
  ├─ Step 5: 更新日志状态 (LogActivity.batchUpdateLogStatus)
  │    └─ COMPLETED / PARTIAL_FAILED / FAILED
  │
  ├─ Step 6: 发送通知 (NotificationActivity.sendBatchNotification)
  │    └─ 通知保密负责人/保卫主管
  │
  ├─ Step 7: Webhook 回调 (WebhookActivity.sendWebhook)
  │    └─ 通知业务系统最终结果
  │
  └─ 返回 PermissionDistributionResult

支持交互:
  ├─ Signal: retryFailedItems  (人工触发失败人员重试)
  └─ Query:  getProgress        (实时查询处理进度)
```

**配置**:

| 项目 | 值 |
|------|-----|
| TaskQueue | `PERMISSION_DISTRIBUTION_TASK_QUEUE` |
| 场景标识 | `permissionDistribution` |
| 最大并发 | 20 |
| QPS 限制 | 20/s |
| Activity | ValidateActivity, LogActivity, CheckTokenActivity, FaceIssueActivity, CardIssueActivity, NotificationActivity, WebhookActivity |
| Signal | `retryFailedItems`（重试失败人员） |
| Query | `getProgress`（返回 DistributionProgress） |

**Activity 配置**:

| Activity | StartToCloseTimeout | 最大重试次数 | 退避策略 |
|----------|---------------------|-------------|---------|
| ValidateActivity | 15s | 3 | 默认 |
| LogActivity | 15s | 3 | 默认 |
| CheckTokenActivity | 15s | 3 | 默认 |
| FaceIssueActivity | 30s | 3 | 初始 2s, 2.0 倍退避 |
| CardIssueActivity | 30s | 3 | 初始 2s, 2.0 倍退避 |
| NotificationActivity | 15s | 5 | 默认 |
| WebhookActivity | 15s | 5 | 默认 |

**限流原理**: 通过 `WorkerOptions.setMaxWorkerActivitiesPerSecond(20.0)` 在 Worker 层控制，避免对富士 API 造成过大压力。

### 4.3 设备数据同步工作流 (DeviceSyncWorkflow)

定时全量/增量同步第三方门禁系统的设备数据到本地业务系统，并通知新设备入库。

**流程图**:

```
开始
  │
  ├─ Step 1: 获取总数 (DeviceSyncActivity.fetchDevicePage 第一页)
  │    └─ 根据响应计算总页数 totalPages
  │
  ├─ Step 2: 并行分页拉取 (Async.function, 并发 parallelPages)
  │    └─ 每页调用 DeviceSyncActivity.fetchDevicePage(pageNo, pageSize)
  │
  ├─ Step 3: 合并数据 (Promise.get 收集所有页)
  │    └─ 合并成完整设备列表 allDevices
  │
  ├─ Step 4: 保存设备 (DeviceSyncActivity.saveDevices)
  │    └─ 通过 webhook 回调业务系统保存/更新设备
  │       ├─ newDevices: 新增设备编码列表
  │       └─ updatedDevices: 更新设备编码列表
  │
  ├─ Step 5: 标记移除 (DeviceSyncActivity.markRemovedDevices)
  │    └─ 本地存在但本次拉取缺失的设备标记 removeFlag=1
  │
  ├─ Step 6: 通知新设备 (DeviceSyncActivity.notifyNewDevices)
  │    └─ 通过 webhook 通知业务系统，由业务系统调用 YxtRebot
  │       通知对应厂区保卫主管
  │
  ├─ Step 7: Webhook 回调 (WebhookActivity.sendWebhook)
  │    └─ 同步完成结果回调
  │
  └─ 返回 DeviceSyncResult
```

**配置**:

| 项目 | 值 |
|------|-----|
| TaskQueue | `DEVICE_SYNC_TASK_QUEUE` |
| 场景标识 | `deviceSync` |
| 最大并发 | 10 |
| Activity | DeviceSyncActivity, WebhookActivity |

**Activity 配置**:

| Activity | StartToCloseTimeout | 最大重试次数 | 退避策略 |
|----------|---------------------|-------------|---------|
| DeviceSyncActivity.fetchDevicePage | 30s | 3 | 初始 2s, 2.0 倍退避 |
| DeviceSyncActivity.saveDevices | 30s | 3 | 默认 |
| DeviceSyncActivity.markRemovedDevices | 15s | 3 | 默认 |
| DeviceSyncActivity.notifyNewDevices | 15s | 5 | 默认 |
| WebhookActivity | 15s | 5 | 默认 |

### 4.4 权限全量初始化工作流 (PermissionInitWorkflow)

从新开普与富士两套系统全量拉取员工门禁权限，合并去重后初始化本地数据库，用于系统初始化或数据修复场景。

**流程图**:

```
开始
  │
  ├─ Step 1: 新开普权限拉取 (并行分页)
  │    └─ 调用 XinkaipuApiClient.getGrantInfo 按员工号分页拉取
  │       并发 parallelPages 个分页任务
  │
  ├─ Step 2: 富士权限拉取 (串行)
  │    └─ 调用富士查询接口拉取权限数据
  │
  ├─ Step 3: 合并去重
  │    └─ 按 (staffNo + deviceCode) 维度去重
  │       统计 deduplicateCount
  │
  ├─ Step 4: 创建初始化日志 (LogActivity.createIssueLogs)
  │    └─ 通过 webhook 通知业务系统写入初始化日志
  │
  ├─ Step 5: Webhook 回调 (WebhookActivity.sendWebhook)
  │    └─ 通知业务系统初始化完成
  │
  └─ 返回 PermissionInitResult
```

**配置**:

| 项目 | 值 |
|------|-----|
| TaskQueue | `PERMISSION_INIT_TASK_QUEUE` |
| 场景标识 | `permissionInit` |
| 最大并发 | 15 |
| Activity | PermissionQueryActivity, LogActivity, WebhookActivity |

**Activity 配置**:

| Activity | StartToCloseTimeout | 最大重试次数 | 退避策略 |
|----------|---------------------|-------------|---------|
| PermissionQueryActivity | 15s | 3 | 默认 |
| LogActivity | 15s | 3 | 默认 |
| WebhookActivity | 15s | 5 | 默认 |

### 4.5 人员变更权限确认工作流 (DepartConfirmWorkflow)

员工部门变动（调岗/离职）时，按部门分组批量处理门禁权限：保留或取消。

**流程图**:

```
开始
  │
  ├─ Step 1: 按部门分组
  │    └─ 将 staffList 按原责任部门 originalDeptCode 分组
  │
  ├─ Step 2: 并行处理每个部门组 (Async.function, 并发 15)
  │    │
  │    ├─ 若 operationType=RETAIN (保留权限):
  │    │    ├─ 2.1 校验 (CheckTokenActivity.checkToken)
  │    │    ├─ 2.2 人脸发行 (FaceIssueActivity.issueFace)
  │    │    └─ 2.3 通知 (NotificationActivity.sendNotification)
  │    │
  │    └─ 若 operationType=CANCEL (取消权限):
  │         ├─ 2.1 校验 (CheckTokenActivity.checkToken)
  │         ├─ 2.2 权限注销 (PermissionCancelActivity.unregisterFace / unregisterCard)
  │         │    └─ 对 3 个固定 GID 分别注销
  │         └─ 2.3 通知 (NotificationActivity.sendNotification)
  │
  ├─ Step 3: 汇总 (Promise.get 收集所有部门组结果)
  │    └─ 统计 successCount / failCount
  │
  ├─ Step 4: Webhook 回调 (WebhookActivity.sendWebhook)
  │    └─ 通知业务系统最终结果
  │
  └─ 返回 DepartConfirmResult
```

**配置**:

| 项目 | 值 |
|------|-----|
| TaskQueue | `DEPART_CONFIRM_TASK_QUEUE` |
| 场景标识 | `departConfirm` |
| 最大并发 | 15 |
| Activity | CheckTokenActivity, FaceIssueActivity, PermissionCancelActivity, NotificationActivity, WebhookActivity |

**Activity 配置**:

| Activity | StartToCloseTimeout | 最大重试次数 | 退避策略 |

| CheckTokenActivity | 15s | 3 | 默认 |

| PermissionCancelActivity | 30s | 3 | 初始 2s, 2.0 倍退避 |

## 6. Activity 层设计

building-access-worker 共 12 个 Activity（接口+实现成对），所有实现类均通过 `@Component` 注册为 Spring Bean，由 TemporalWorkerConfig 注册到对应 Worker。

| 序号 | Activity 接口 | 实现类 | 依赖 Client | 用途 |
|------|--------------|--------|-------------|------|
| 1 | CheckTokenActivity | CheckTokenActivityImpl | FujiApiClient | 发行校验，校验卡号/人脸是否已有发行信息 |
| 2 | FaceIssueActivity | FaceIssueActivityImpl | FujiApiClient | 人脸发行，向设备下发人脸权限（OperType=0） |
| 3 | FaceModifyActivity | FaceModifyActivityImpl | FujiApiClient | 人脸改写，修改已发行的人脸权限（OperType=1） |
| 4 | CardIssueActivity | CardIssueActivityImpl | FujiApiClient | 卡发行，向门禁设备下发卡权限 |
| 5 | FaceIncrementActivity | FaceIncrementActivityImpl | FujiApiClient | 增量权限，按 powerType 增加/删除指定设备权限 |
| 6 | PermissionCancelActivity | PermissionCancelActivityImpl | FujiApiClient | 权限注销，对 3 个固定 GID 分别注销人脸/卡权限；并支持按手机号查询卡号 |
| 7 | WebhookActivity | WebhookActivityImpl | OkHttp | Webhook 回调通知业务系统 |
| 8 | DeviceSyncActivity | DeviceSyncActivityImpl | XinkaipuApiClient + Webhook | 设备同步：拉取单页/保存/标记移除/通知新设备 |
| 9 | PermissionQueryActivity | PermissionQueryActivityImpl | XinkaipuApiClient | 权限查询，查询新开普授权信息（单个/批量） |
| 10 | LogActivity | LogActivityImpl | Webhook | 日志管理，创建/更新/批量更新下发日志状态 |
| 11 | NotificationActivity | NotificationActivityImpl | OkHttp | 消息通知，通过 YxtRebot HTTP 发送通知（单个/批量） |
| 12 | ValidateActivity | ValidateActivityImpl | Webhook | 校验：白名单校验、设备权限校验、批量过滤白名单人员 |

### 6.1 CheckTokenActivity

```java
@ActivityMethod
CheckTokenResponse checkToken(CheckTokenRequest request);
```

调用 `FujiApiClient.checkTokenState`，异常通过 `Activity.wrap(e)` 包装后抛出，触发 Temporal 重试。

### 6.2 FaceIssueActivity / FaceModifyActivity

```java
@ActivityMethod
FaceIssueResponse issueFace(FaceIssueRequest request);   // 发行

@ActivityMethod
FaceIssueResponse modifyFace(FaceIssueRequest request);  // 改写
```

两者均调用富士接口，区别在路径与 OperType/StafFState 参数。

### 6.3 CardIssueActivity

```java
@ActivityMethod
CardIssueResponse issueCard(CardIssueRequest request);
```

### 6.4 FaceIncrementActivity

```java
@ActivityMethod
FaceIssueResponse modifyByPowerType(FaceIncrementRequest request);
```

通过 `powerType` 区分增加（0）或删除（1）设备权限，只影响 `AuthorizeDeviceNo` 中指定的设备。

### 6.5 PermissionCancelActivity

```java
@ActivityMethod
boolean unregisterFace(List<UnregisterRequest> requests);  // 注销人脸（多GID）

@ActivityMethod
boolean unregisterCard(List<UnregisterRequest> requests);  // 注销卡（多GID）

@ActivityMethod
String queryCardNo(String phone);  // 按手机号查询卡号
```

注销方法对 3 个固定 GID 分别调用 `FujiApiClient.unregister`，任一 GID 失败则返回 false（不抛异常，由工作流决定如何处理）。`queryCardNo` 从 `FujiApiClient.getByFunc` 响应中提取 `Reserve2` 字段作为卡号。

### 6.6 WebhookActivity

```java
@ActivityMethod
boolean sendWebhook(String payload);
```

向 `webhook.callback.url` 发送 JSON POST 请求，HTTP 5xx 抛出异常触发重试。

### 6.7 DeviceSyncActivity

```java
@ActivityMethod
List<Map<String, Object>> fetchDevicePage(DeviceSyncActivityRequest request);

@ActivityMethod
boolean saveDevices(List<Map<String, Object>> devices, String deviceType);

@ActivityMethod
boolean markRemovedDevices(List<String> deviceCodes);

@ActivityMethod
boolean notifyNewDevices(List<String> deviceCodes);
```

`fetchDevicePage` 调用 `XinkaipuApiClient.getAccessTermAreaInfo` 拉取设备；其余三个方法通过 webhook 回调业务系统 API（路径由 `device.sync.save-path` / `mark-removed-path` / `notify-new-path` 配置）。

### 6.8 PermissionQueryActivity

```java
@ActivityMethod
Map<String, Object> queryGrantInfo(String outid);

@ActivityMethod
List<Map<String, Object>> batchQueryGrantInfo(List<String> outids);
```

调用 `XinkaipuApiClient.getGrantInfo`。批量查询对单个失败做容错，将失败项标记 `success=false` 并继续处理其余项。

### 6.9 LogActivity

```java
@ActivityMethod
List<Integer> createIssueLogs(List<Map<String, Object>> logs);

@ActivityMethod
boolean updateLogStatus(int logId, String status, String remark);

@ActivityMethod
boolean batchUpdateLogStatus(List<Integer> logIds, String status);
```

通过 webhook 调用业务系统 API（路径由 `log.api.create-path` / `update-status-path` / `batch-update-status-path` 配置）。`createIssueLogs` 从响应中解析日志 ID 列表。

### 6.10 NotificationActivity

```java
@ActivityMethod
boolean sendNotification(String messageType, String recipient, String content);

@ActivityMethod
boolean sendBatchNotification(String messageType, List<String> recipients, String content);
```

通过 `notification.yxtrebot.url` 配置的 YxtRebot 机器人地址发送 HTTP POST 通知。

### 6.11 ValidateActivity

```java
@ActivityMethod
boolean validateWhitelist(String staffNo);

@ActivityMethod
boolean validateDevicePermission(String staffNo, List<Integer> deviceNos);

@ActivityMethod
List<StaffInfo> filterWhitelistStaff(List<StaffInfo> staffList);
```

通过 webhook 调用业务系统校验 API（路径由 `validate.api.whitelist-path` / `device-permission-path` 配置）。`filterWhitelistStaff` 内部循环调用 `validateWhitelist`，对单个人异常做容错。

## 8. 重构对比

本次重构将原 safety-service-master 中的门禁业务编排下沉到独立的 Temporal Worker，下表对比重构前后的差异。

### 8.1 整体架构对比

| 维度 | 重构前（safety-service-master） | 重构后（building-access-worker） |
|------|--------------------------------|----------------------------------|
| 业务编排位置 | safety-service-master Handler/Service 层 | 独立 Temporal Worker 进程 |
| 长链路编排方式 | 同步代码调用 + 数据库状态机 | Temporal Workflow 编排，Activity 自动重试 |
| 失败重试 | 手动补偿 + 定时任务扫描 | Temporal RetryOptions 自动重试，可配退避策略 |
| 进度可观测 | 查数据库日志表 | Workflow Query（getProgress）实时查询 |
| 人工干预 | 修改数据库状态 | Workflow Signal（retryFailedItems）触发 |
| 限流保护 | 自实现信号量/线程池 | WorkerOptions.setMaxWorkerActivitiesPerSecond |
| 业务系统职责 | 编排 + CRUD + 第三方调用 + 通知 | 仅 CRUD + Webhook 接收 |
| 部署独立性 | 与安全业务耦合部署 | 独立容器，可按场景扩缩容 |

### 8.2 大规模权限下发对比

| 维度 | 重构前 | 重构后 |
|------|--------|--------|
| 并发控制 | 自实现线程池，并发不可动态调整 | WorkerOptions.setMaxConcurrentActivityExecutionSize(20) |
| QPS 限流 | 无统一限流，易压垮富士 API | setMaxWorkerActivitiesPerSecond(20.0) |
| 失败重试 | 全量重试或人工处理 | 失败人员通过 Signal 触发重试，不影响已成功人员 |
| 进度查询 | 查日志表 | Query getProgress 实时返回 |
| 日志一致性 | 多步操作可能中途失败导致日志状态不一致 | Workflow 保证最终一致，Activity 幂等 |

### 8.3 设备数据同步对比

| 维度 | 重构前 | 重构后 |
|------|--------|--------|
| 同步方式 | 单线程串行分页，耗时长 | 并行分页拉取（parallelPages 并发），耗时大幅缩短 |
| 失败恢复 | 全量重跑 | 单页失败仅重试该页 |
| 新设备通知 | 与同步逻辑耦合 | 独立 Activity，可单独重试 |

### 8.4 权限全量初始化对比

| 维度 | 重构前 | 重构后 |
|------|--------|--------|
| 多源合并 | 串行拉取新开普 + 富士，再合并 | 新开普并行分页 + 富士串行，合并去重独立步骤 |
| 去重 | 业务代码内嵌 | 独立步骤，deduplicateCount 可统计 |
| 可重试 | 整体重跑 | 分页任务粒度重试 |

### 8.5 人员变更权限确认对比

| 维度 | 重构前 | 重构后 |
|------|--------|--------|
| 部门分组 | 同步代码循环 | Workflow 内 Async.function 按部门组并行 |
| 保留/取消分支 | if-else 嵌套 | 工作流清晰分支，独立 Activity 编排 |
| 通知一致性 | 通知失败可能丢失 | NotificationActivity 重试 5 次 |

## 10. 开发指南

### 10.1 新增工作流

1. 在 `workflow/` 下创建 `@WorkflowInterface` 接口，定义 `@WorkflowMethod` 入口方法；如需人工干预，增加 `@SignalMethod`；如需进度查询，增加 `@QueryMethod`。
2. 在 `workflow/impl/` 下创建实现类，通过 `Workflow.newActivityStub(ActivityInterface.class, activityOptions)` 创建 Activity 代理。
3. 在 `TemporalWorkerConfig` 中：
   - 新增 TaskQueue 常量
   - 新增 Worker 注册块，绑定 TaskQueue、Workflow 实现类、Activity 实现类
   - 如需限流，通过 `WorkerOptions` 配置并发数与 QPS
4. 在 `application.yml` 的 `worker.scenarios` 默认值中追加新场景标识。

### 10.2 新增 Activity

1. 在 `activity/` 下创建 `@ActivityInterface` 接口，定义 `@ActivityMethod` 方法。
2. 在 `activity/` 下创建 `@Component` 实现类，注入所需的 ApiClient 或 OkHttpClient。
3. 实现中：
   - 异常通过 `Activity.wrap(e)` 包装后抛出，由 Temporal 触发重试
   - 必须保证幂等性（同一输入多次执行结果一致）
   - 使用 `@Value` 注入配置项（路径、URL 等）
4. 在 `TemporalWorkerConfig` 中将 Activity 实现类注册到对应 Worker。

### 10.3 新增第三方设备接口

1. 在 `client/` 下创建新的 API Client（如 `DahuaApiClient`），封装 HTTP 调用：
   - OkHttpClient 设置 connectTimeout=5s, readTimeout=15s
   - HTTP 5xx 抛出 RuntimeException 触发上层 Activity 重试
2. 在 `activity/` 下创建对应的 Activity 接口和实现。
3. 在 `application-*.yml` 中添加新设备的配置（base-url、路径、认证参数）。
4. 在 `TemporalWorkerConfig` 中注册新的 Worker 场景或扩展现有工作流按 `deviceType` 分发。

### 10.4 调整限流参数

修改 `TemporalWorkerConfig.java` 中对应 TaskQueue 的 Worker 配置：

```java
Worker worker = factory.newWorker(TASK_QUEUE_PERMISSION_DISTRIBUTION,
        WorkerOptions.newBuilder()
                .setMaxConcurrentActivityExecutionSize(20)    // 最大并发数
                .setMaxWorkerActivitiesPerSecond(20.0)         // QPS 限制
                .build());
```

### 10.5 开发规范

- **Workflow**: 纯逻辑编排，不直接调用外部服务；使用 `Workflow.getLogger()` 和 `Workflow.currentTimeMillis()`；不可直接 `new Date()` 或 `Thread.sleep()`。
- **Activity**: 必须保证幂等性；异常通过 `Activity.wrap(e)` 包装后抛出；重业务逻辑放在 Activity，Workflow 只负责编排。
- **Client**: 必须设置连接超时（5s）和读取超时（15s）；HTTP 5xx 抛出异常触发重试；4xx 按业务语义处理。
- **命名约定**:
  - Workflow 接口：`{业务名}Workflow`
  - Activity 接口：`{业务名}Activity`
  - Client：`{系统名}ApiClient`
  - TaskQueue 常量：`TASK_QUEUE_{大写业务名}`
  - 场景标识：`{小驼峰业务名}`
